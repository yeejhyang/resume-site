一、项目介绍与详细技术细节

一句话介绍项目（电梯陈述）

本项目的定位是多路混合检索与知识图谱驱动的研发知识检索平台；它面向所有"想快速了解某个技术方向、搞清某个领域"的人——在校研究生、工程师；以 arXiv 学术论文为落地场景，覆盖「文档入库 → 多路检索 → 意图理解 → 模型生成 → 溯源反馈」的完整链路，核心是问题理解与意图路由、四通道并行召回 + RRF 融合、两级精读 + ReAct 编排，实现带溯源回答的端到端闭环。

它和传统的 RAG 有什么不同？

先给直觉：传统 RAG 是"单路问答"，本项目是"懂行的多路检索平台"。传统 RAG 一般是「一个向量库 + 一次相似度检索 + 拼进 prompt 生成」，比较"朴素"；本项目在它基础上做了四层进阶：

  • ① 从"单路召回"到"多路混合召回"：传统 RAG 只靠向量语义相似度一路召回，对精确编号、专有名词、引用链多跳、"库里没有"的问题容易漏。本项目四通道（向量 Milvus / 关键词 BM25 / 知识图谱 LightRAG / 联网搜索）并行召回 + RRF 融合 + Rerank 精排，把"找得全"和"排得准"解耦，实测较单路向量 Recall@10 提升 12.3%。
  • ② 从"无脑检索"到"意图理解 + 路由"：传统 RAG 不区分问题类型，一律按相似度查同一个库；本项目先用 LLM 打分 + 树形意图识别，把复杂问题重写、拆分成子问题，再路由到对应知识库或 MCP 工具（如精读论文），还能自动衔接「先定位论文 → 再拉全文精读」两级联动。
  • ③ 从"全文入库"到"两级精读"：传统 RAG 把文档全文向量化入库（索引膨胀 + 召回噪音）；本项目只索引摘要（单篇约 0.2KB），第一级低成本召回定位"是哪几篇论文"，第二级按需经 MCP 实时拉 arXiv 全文精读技术细节。
  • ④ 从"单图/单模型"到"多图谱 + 模型工程化"：引入知识图谱支持引用链多跳推理；服务端抽象多供应商模型客户端 + 三态熔断降级 + 流式输出，并用 Redis/RocketMQ 做工程保障。

一句话：传统 RAG 回答"相关不相关"，本项目追求"理解意图 → 多路找全 → 精排找准 → 溯源作答"的完整闭环，更接近一个生产级研发知识检索平台。

系统是如何建立知识库的？

先给直觉：知识库不是"塞进去一坨文档"就完事，而是每条数据都要同时做成"可语义检索、可精确匹配、可图谱多跳、可溯源"的形态。以 arXiv 论文入库为例，走一条「上传 → 分块 → 多渠道索引 → 异步入库」的流水线：

1 文档上传 2 清洗/解析 3 分块 4 向量化 + 写向量库 5 同步关键词索引 6 图谱抽取实体/关系 7 落库(metadata)
  • 上传与清洗：文档上传接口接收文件，附带 metadata（如 category 学科类别），解析正文并清洗格式。
  • 分块（chunking）：把长文档切成语义相对完整的块，块太小上下文割裂、太大信息稀释，再逐块做 Embedding。
  • 多渠道索引（核心）：一次入库同时建立多套索引——① 向量写进 Milvus（title+abstract+arxiv_id+metadata）；② 关键词写进 ES 做 BM25；③ 图谱由 GraphSyncingVectorStoreService 在向量入库时自动抽取实体和关系写入 LightRAG 图存储（Neo4j），不用手动建图。这就是"四通道"各自有料可查的根基。
  • 异步入库 + 幂等：入库/分块/删除这类重活通过 RocketMQ 异步处理，配合事务消息 + 幂等保证任务不重不漏，不阻塞检索主链路。
  • 两级精读的落点：学术库只存「标题 + 摘要 + arxiv_id」（单篇约 0.2KB），全文不上库、按需实时拉取——这样既覆盖百万级论文，又控制存储与噪音。

一句话：知识库 = 同一个文档被同时"向量化、关键词化、图谱化"成多份可检索形态，并带结构化 metadata 支撑学科过滤与溯源。

用户的一次提问，系统内部是怎么一步步处理的？（通俗版流程）

先给直觉：这个平台就是一个"懂行的检索助手"。你抛一个问题，它内部走三步——① 听懂问题并分流 → ② 多路去找 → ③ 层层筛选出最靠谱的几段。展开讲：

  1. 问题理解与意图路由：大模型先把复杂问题重写、切分成最小的子问题，再根据 LLM 打分，判断每个子问题该走哪个意图路由——也就是该查哪个知识库、要不要调用某个外部工具（如精读论文的 MCP 工具）。
  2. 四路并行召回：意图定下来后，针对每个子问题同时用 4 种方式召回（向量语义 / 关键词 / 知识图谱 / 联网搜索），先把候选资料"广撒网"捞一批出来。
  3. RRF 融合 + Rerank 精排：把 4 路结果按"名次"加权合并，粗排出 Top50，再换成更精细的精排模型，选出最相关的 Top10，最终拼成带引用的上下文交给大模型生成，返回给用户。

下面就从"问题理解与意图路由"这个入口环节开始，逐块展开每个环节的技术细节。

整体架构（一句话）

前后端分离的「模块化单体」——后端按职责拆成 4 个 Maven 模块，各管各的：framework（通用基础设施）、infra-ai（AI 能力层，封装各家大模型/向量库）、bootstrap（RAG 业务主流程）、mcp-server（独立的 MCP 工具服务，供模型调用外部工具）。

这么分层的好处用一个场景就说明白：想换个模型供应商、或换套向量数据库，只需改 infra-ai 里的实现，业务主流程一行不用动。把「业务编排、AI 供应商差异、通用基础设施」三件事隔离开，互不干扰，维护起来清晰很多。

一次提问的完整调用链路（整体印象）
1 查询重写 2 多问题拆分 3 意图识别路由 4 多路并行召回 5 去重 6 RRF 融合 7 Rerank 精排 8 富化 9 拼上下文(带引用) 10 流式生成 11 溯源反馈

用一个真实问题把整条链路串起来——「RAG 最新进展？内部有没有相关方案？再精读那篇多模态 RAG 论文」：系统先把这句话重写、拆成三个子问题，分别命中 paper（查论文）/ internal-tech（查内部文档）/ paper-detail（精读论文）三个意图，各自路由到不同的库或工具；每个子问题内部再做「四通道并行召回 → RRF 融合 → Rerank 精排」；第三个子问题走两级精读（先搜摘要定位 → 自动提取论文编号 → 经 MCP 实时拉全文）；最后把各部分结果合并，走模型路由（含熔断）流式输出带引用的回答。

简单说：一次提问 = "读懂问题 → 分流到多个库去找 → 各自精挑 → 汇总成答案"，下面从第一步"读懂问题"开始拆解。

模块一 · 问题理解与意图路由（简历句②：Query 改写 + 树形意图识别）

意图识别是怎么做的？（学科→方向→子方向）

先给直觉：系统得先"听明白"你在问哪类问题，才知道去哪个库找、要不要调工具。这一步不是靠关键词硬匹配，而是让大模型"打分"判断。具体分几步：

  • 并行分类：核心类 IntentResolver 拿到重写+拆分后的多个子问题，用 CompletableFuture.supplyAsync(..., intentClassifyExecutor) 对每个子问题并行分类，而不是一个个等。
  • LLM 打分 + 过滤：分类器 IntentClassifier 基于 LLM 打分，给每个意图节点打分，再用 filter(score >= INTENT_MIN_SCORE) 筛掉低分、limit(MAX_INTENT_COUNT) 限制数量。
  • 树形结构：意图本身是一棵「学科 → 方向 → 子方向」的层级树（存在 IntentNode，由 IntentTreeFactory / IntentTreeCacheManager 构建与缓存），支持由粗到细逐层定位。
  • 数量保底策略（capTotalIntents）：当子问题太多、意图总数超限时，每个子问题至少保留 1 个最高分意图，剩下的配额再按分数从高到低分——避免某个子问题被"剃光头"导致漏检索。
  • 万一分类本身失败，降级为空意图放行，不影响整体流程。
「KB 召回节点 + MCP 精读节点」两级意图联动路由是怎么设计的？（核心创新）

针对学术论文「先检索、再精读」的场景，普通单级意图路由要么只召回摘要、要么直接调工具，无法自然衔接「先定位是哪篇论文、再拉全文精读」。我设计了两级意图联动路由：

第一级 KB 召回节点（paper） 学术摘要库全局召回 → 命中摘要（含 arxiv_id） 命中上下文注入 第二级 MCP 精读节点（paper-detail） LLM 自动提取 arxivId → 拉全文精读
  • 第一级 paper（KB 召回节点）：驱动学术摘要库 paperarxivstore 全局召回，返回命中摘要及其元信息 arxiv_id。
  • 两级衔接（关键）：将第一级命中摘要（含 arxiv_id）作为「命中上下文」注入第二级 MCP 工具 arxiv_fetch_fulltext 的参数提取阶段，由 LLM 从「用户问题 + 命中摘要」中自动抽取 arxivId，驱动全文拉取——用户全程无需手输论文编号。
  • 参数提取防坑：McpParameterExtractor.extractParametersWithContext(...) 的参数提取 Prompt 刻意移除示例编号，并强化「必须从命中资料实际内容提取、禁止沿用示例/编造」的约束，避免 LLM 照抄示例而非提取真实编号。
  • 兜底：MCP 精读节点本身也绑定学术库 collection，即使第一级 KB 召回节点没单独命中，也能驱动学术库召回，保证命中上下文里总有 arxiv_id 的来源。

这条联动路由就是 「abstract 全局召回 + 按需拉取 arXiv 全文」两级精读 在意图层的落地点：第一级低成本、广覆盖地"定位是哪几篇论文"，第二级按需、局部地"精读具体技术细节"。

多知识库路由和"定向 vs 全局"检索怎么决策？

先给直觉：判断出意图后，系统面临一个选择——"我很确定该去哪个库"还是"我不太确定、那就到处都搜一下"。对应两种策略：

  • 多知识库路由：根据意图识别结果，把子问题送进对应的知识库；同时支持 MCP 工具意图，像"查天气/查票务"这类请求直接路由到外部工具，不进知识库。
  • 定向 vs 全局（RetrievalScopeResolver）：只看知识库意图的最高分，只有高到越过 confidenceThreshold 才收窄到那个库（定向检索）；否则保守起见，走全局检索（所有库都找）。
  • 兜底设计（很关键）：即使是定向检索，也会额外给"没被选中的库"分配固定候选名额（supplementRatio）——万一意图判错了，其他库还能捞回点东西，避免一判错就彻底漏召回。
查询词映射和问题重写解决什么问题？

一句话：把"用户的话"先翻译成"机器好检索的话"，发生在检索之前，是"检索质量的前置保障"。

  • 查询词映射：把用户口语化的词映射成规范术语/同义词。比如用户说"深度学习模型那篇"，文档里写的是"神经网络"，不翻译一下关键词检索就会漏——把两边对齐，就补上了这个坑。
  • 多问题重写拆分：一是补全指代——多轮对话里用户说"那它和 B 方法比呢"，"它"指什么需要结合上文补齐；二是拆分复杂问题——一个大问题拆成几个子问题分别检索再合并，召回质量更高。
意图路由的量化效果？
  • 自建评测集：基于真实检索日志构造 + 人工抽检标注。
  • 指标：意图路由 Top-1 准确率 92.5%——即系统打分最高的那个意图叶子节点与人工标注一致的比例，衡量"分流这一环"判得准不准。
  • 面试提示：Top-1 只衡量意图分类本身，不代表"最终回答准确率"，要能讲清它为什么单独列在"问题理解与意图路由"下。

模块一 · 附：分库方案（功能分层为主、学科交给意图树）

知识库是怎么分库的？为什么这么分？

场景是「以学术论文为载体的通用研发知识检索平台」。知识库有两个互相独立（正交）的切分维度，可以叠加用：

  • 按"用途/形态"切（功能维度）——对应「摘要库 vs 全文 vs 引用图谱」，正是两级精读的思路；
  • 按"学科领域"切（内容维度）——对应意图树里的「学科 → 方向 → 子方向」层级。

我的原则一句话：库按功能分层来分，学科的细分交给意图树去处理。为什么学科不拆成库？打个比方，图书管理员不会给每本书按"图书分类号"单独建一个书库——因为一本书可能同时属于多个分类（"多模态 RAG"算 CV 还是 NLP？边界模糊），而且分类多到爆炸（arXiv 有几十个类别）。更重要的是，学科怎么路由，意图树已经做了，再在库层面切一遍是重复劳动。

多知识库具体怎么设计？（功能分层为主）

我的知识库按「检索方式」分层，而不是按学科切。最终落地为「2 个逻辑库 + 2 个检索通道」：

形态名称内容用途检索方式
逻辑库 ★核心paperarxivstore（学术摘要库）标题 + 摘要 + arxiv_id + 元数据（作者/年份/类别）第一级全局召回，定位「是哪几篇论文」向量（Milvus）+ 关键词（ES BM25）双索引
逻辑库 ★扩展internal_docs（内部研发知识库）公司/团队内部研发文档、技术方案、Wiki回答「我们内部怎么做的」私有知识问题向量 + 关键词（复用同一套引擎）
检索通道引用图谱（LightRAG）论文引用关系、方法演进关系（实体+关系图）引用链多跳推理、脉络追踪图谱检索（naive/local/global/hybrid/mix）
检索通道联网搜索（You.com）—（实时工具，非知识库）时效兜底，补库里没有的最新内容联网搜索

关键认知——图谱不是「库」，是「通道」：图谱的数据不在向量库里，而是存在 LightRAG 内部的图存储（Neo4j）。它靠 GraphSyncingVectorStoreService 在文档向量入库时，自动顺带抽取实体和关系，不用你手动建库灌数据。所以它和向量、关键词、联网平级，本质是第五种"检索方式"（通道），而不是第四个存放内容的库。

为什么摘要库必须独立：它是两级精读的第一级，单篇约 0.2KB、成本极低、覆盖面最广，是整个系统的「入口」。如果摘要和全文混在一个库里，两级精读就退化成了普通全文检索，所以它必须单独存在——这是底线。

为什么图谱独立于向量库：图谱是图结构数据，存储和检索方式和向量、关键词完全不同，硬混在一起会让向量库"图不图、文不文"。且图谱构建成本高，独立开方便按需重建。

分库怎么对应到意图路由？

分好库后，意图树节点通过 collection_names（JSONB 数组）绑定一个或多个库，路由时按命中意图定向到对应库/通道：

意图节点类型路由到
paperKB 召回节点paperarxivstore（学术摘要库）
paper-detailMCP 精读节点paperarxivstore 召回摘要 → MCP arxiv_fetch_fulltext 拉全文
paper-citation / 引用链KB 召回节点图谱通道（LightRAG 多跳推理）
internal-techKB 召回节点internal_docs（内部文档库）
最新进展工具节点联网搜索（You.com）
一个真实请求怎么在多库之间路由？

用户问：「RAG 最新技术进展，以及我们内部有没有相关的技术方案」

经过查询重写 + 多问题拆分，拆成两个子问题，分别定向到不同库：

  • 子问题①「RAG 最新技术进展」→ 命中 paper → 查 paperarxivstore（摘要库）+ 联网兜底补时效；
  • 子问题②「内部有没有相关技术方案」→ 命中 internal-tech → 查 internal_docs（内部文档库）。

这里「多库路由 + 定向 vs 全局」的价值真正体现出来了：两个子问题分别定向到不同库。单库场景下这些机制会退化成摆设，只有多库才「有真实用武之地」。

为什么保留「内部文档库」这个库？它和纯学术问答工具的区别在哪？
  • 项目定位是「通用研发知识检索平台」，arXiv 只是「落地验证场景」，不是全部。
  • 真正的通用性体现在能接入内部私有知识——这是和纯学术问答工具的本质区别，也是「平台化」思维的体现。
  • 叙事角度：同一套多路检索 + 两级精读引擎，既能查 arXiv 学术论文，也能接入企业内部研发文档、代码库、Wiki——这才是「通用」二字的真义，而不是一个只能查论文的 demo。
这套分库方案是怎么一步步演进出来的？

一句话：不是一步到位堆功能，而是"先把核心跑通，再一层层往通用方向加"。总共三步：

  • 第一步（单库跑通核心）：只做 paperarxivstore（摘要库）+ 联网工具，先把两级精读这条核心链路打通（摘要召回 + MCP 拉全文）——这是整个平台最该讲透的亮点。
  • 第二步（体现平台通用性）：接入 internal_docs 内部文档库，让「多库路由 / 定向 vs 全局」这些机制真正有了用武之地——否则单库下它们就是摆设。
  • 第三步（补全检索维度）：启用 LightRAG 引用图谱，让 GraphSyncingVectorStoreService 在向量入库时自动抽取实体/关系，补上「引用链 / 方法演进」这条多跳推理通道。
  • 演进逻辑：每一步都站在"上一步已经跑通"的基础上，往「更通用、更多检索维度」方向加一层，而不是一步到位堆功能。
arXiv 的学科类别（cs.CL / cs.AI / cs.CV…）要不要也拆成库？

不要。学科类别是「字段」，不是「库」。它和功能分库是两个正交维度，叠加但不混用：

  • 为什么不能拆成 7 个库：因为一篇论文可以同时属于多个学科（categories = "cs.CL cs.AI"，用空格列了好几个标签）。一旦物理拆库就会陷入"这本书该放图书馆哪个书架"的难题——放这个库就漏了另一个，放多个库就重复索引；而且 cs.AI / cs.LG / stat.ML 高度重叠，边界本来就模糊。
  • 学科路由交给意图树：意图树本来就是「学科 → 方向 → 子方向」层级，学科该去哪已经由它管了，再在库层面切一遍纯属重复。
  • 正确的用法：库内字段过滤——把学科类别做成结构化元数据字段（而不是正文里的一行文本），检索时用条件过滤收窄：collection_name == "paperarxivstore" && metadata["category"] == "cs.CL"。这样既保住了"一个摘要库"的两级精读，又能做到学科定向，还天然支持"一篇论文多类别"和"跨学科问题"（多模态 RAG 算 CV 还是 NLP，直接都命中）。

为此我把「category 作为结构化元数据」的完整链路落地了，分三段：

  • 入库侧：文档上传接口新增 metadata 字段（JSON），落 t_knowledge_document.metadata 列；分块时经 DocumentRef.metadata 透传，在 DefaultIngestionKernel 里合并进每个块的 ChunkMetadata.extras，最终随 toMap() 写进向量库 metadata。
  • 脚本侧：batch_ingest_arxiv.py 的 build_metadata() 从 category_list 提取主类别 + 完整列表，以 {"category":"cs.CL","category_list":["cs.CL","cs.AI"]} 作为 metadata 随文档上传。
  • 检索侧：MilvusVectorRetrieverService 把 RetrieveRequest.metadataFilters 拼进标量过滤表达式 metadata["key"] == "value"，与 collection 过滤 AND 组合，实现对 category 的精确等值过滤。
一句话总结分库方案？

功能分层为主（摘要库 + 内部文档库两个逻辑库，图谱与联网作为独立检索通道），学科细粒度交给意图树，联网搜索作为时效工具兜底。这样既保住了两级精读的核心亮点，又让「多库路由」真正成立，还撑起了「通用研发知识检索平台」的定位。

模块二 · 多路混合检索（简历句①：四通道并行召回 + RRF 融合 + Rerank）

一个子问题的完整检索流程（以「RAG 最新进展？」为例，建立整体印象）
1 问题理解 2 四路并行召回 3 RRF 融合(→Top50) 4 Rerank 精排(→Top10) 5 拼上下文生成
  1. 问题理解：先让大模型给子问题做意图打分，判断它该去哪个知识库、要不要调外部工具（比如命中了 paper 意图 → 就去查学术摘要库 paperarxivstore）。
  2. 四路并行召回：同时用 4 种方式各找一批资料——向量检索（Milvus，按语义找相似的）、关键词匹配（ES BM25，按字面精确找）、知识图谱（LightRAG，沿关系多跳追踪）、联网搜索（You.com）。每路都返回自己的候选和内部排名，像 4 个"海选评委"各推荐一拨人。
  3. RRF 融合（→Top50）：4 路给的分数量纲完全不同（余弦 0.85 / BM25 18.6 / 图谱 3.2），没法直接相加。RRF 干脆不看分数、只看"名次"来合并成统一排名，再截断候选池到 Top50（rerankCandidateLimit），进入下一轮。
  4. Rerank 精排（→Top10）：RRF 只看名次、没真正"读懂"内容，精度不够。这里换成 cross-encoder（交叉编码器），把问题和每个候选拼在一起逐字比对打精确分，留下最相关的 Top10。
  5. 拼上下文生成：把 Top10 补上元数据、编上引用号，拼成上下文交给大模型生成答案。

一句话概括这套检索漏斗：「快而糙的召回（向量）→ RRF 合并名次（→50）→ 慢而准的精排（→10）」，本质就是「海选 → 笔试 → 面试」——先广撒网捞出一大批，再用越来越精细的方式层层筛选，平衡"快"和"准"。

四通道是如何设计并行的？

设计思路一句话：把 4 个"找资料的专员"统一封装、同时派出去，任何一个掉链子都不拖累整体。具体落到代码上是三层：

  • 统一"接口"：4 个通道都实现同一个 SearchChannel 接口（search() 检索、isEnabled() 是否启用等），对外都返回统一的 SearchChannelResult。这样上层主流程只用管一套接口，具体是向量/关键词/图谱/联网由各通道自己实现。
  • 并行调度：核心编排类 MultiChannelRetrievalEngine 先过滤掉关闭的通道，再用 CompletableFuture.supplyAsync(..., ragRetrievalExecutor) 把 4 路提交到专用线程池，同时开跑而不是一个接一个等。
  • 失败/超时都"单路降级"：每路用 catch(Exception) 包住，挂了就返回空结果，绝不让一路拖垮整条链；超时用 future.orTimeout(timeoutMs)——只放弃这一路的结果、但不强行终止任务，因为最慢的一路不该拖住其余 3 路的成果融合。
四通道各擅长什么？举个具体问题看它们怎么互补？

以学术论文场景为例，同一个知识库，不同问法需要不同通道兜住：

用户问法最优通道为什么
"检索增强生成有哪些综述？"向量语义相近，向量检索能召回"Retrieval-Augmented Generation"相关的综述论文
"论文 2503.10677 是哪篇？"关键词（ES BM25）精确编号匹配，向量对"数字编号"不敏感，关键词通道精确命中
"谁引用了 Attention is All You Need？"知识图谱引用链是多跳关系，图检索沿"引用边"追踪，向量/关键词都做不到
"RAG 最新进展（2026）？"联网搜索库里没有的最新论文，联网补时效

关键结论：单靠向量一条路，上面 4 种问法至少漏掉一半。这正是"多路召回 + 融合"的动机——就好比查资料不能只靠搜索引擎，还得靠图书馆目录、熟人打听、实时新闻，不同通道覆盖不同问法，合并起来才不容易漏。

RRF 加权融合是怎么实现的？（关键，面试必问）

先给直觉：4 路评委各给了一份"候选人名次表"，但打分风格完全不同。RRF 的做法是——不看绝对分数，只看"名次"，名次越靠前加分越多；同时给可信度高的通道更高的"话语权"（权重）。

  • 公式：score(chunk) = Σ_channel weight_channel / (k + rank_channel)，rank 从 0 开始（即 weight / (k + rank + 1)）。k 的作用是缩小名次差距的影响（名次第 1 和第 2 的差别，远小于分数 100 和 90 的差别），让融合更"温和"。
  • 为什么加权：不同通道可信度不同。例如跑在全局图上的图谱通道噪声偏高，就给它降权，避免噪声通道靠"硬凑名次"挤进前排。
  • 权重和 k 值都能配置（fusion.channel-weights、fusion.rrf-k），方便调优。
  • 关键细节：名次取自不可变的原始召回顺序。即使上游去重合并了 chunks，也不丢失"多路命中"信息——一个片段被越多路同时命中，说明它越相关，RRF 天然给它加分。
  • 只有 results.size() > 1（确实多通道）才做 RRF，单通道保持原顺序；融合后按分倒序截断候选池到 rerankCandidateLimit，只把高分的前 N 名送去 Rerank。
后处理链（去重 → 融合 → 精排 → 富化）如何串联？

先给直觉：4 路召回回来的是"一锅乱料"，还要经过"去重、合并名次、精排、补信息"这几道流水线工序才能变成能用的上下文。我用责任链模式实现——每个处理器按 getOrder() 从小到大依次执行，任何一环出错只 log.error 并跳过，绝不中断整条流水线：

Order处理器职责
1DeduplicationPostProcessor按 RetrievedChunkKey 去重（putIfAbsent 保留首次出现）
5FusionPostProcessorRRF 加权融合 + 截断候选池
10RerankPostProcessorRerank 精排，输出 contextTopK 条
20MetadataEnrichmentPostProcessor按 chunkId/docId 回表补元数据（docId/docName/chunkIndex），只富化不重排

Rerank 阶段还做了归因日志：对比 Rerank 前后各通道候选数，重点观测"图谱证据存活率"，用于指导图谱通道权重调优。

为什么 RRF 只看排名、Rerank 要换 cross-encoder？两段式各解决什么？（高频追问）
  • RRF 为什么只看排名不看原始分数：向量（余弦）、ES（BM25）、图谱、联网四通道的分数量纲完全不同（0.85 vs 18.6 vs 3.2），像"1 米长的绳子"和"3 公斤重的石头"根本没法直接比。而排名（第 1、第 2…）天然是同一把尺子，用 weight/(k+rank) 就能公平合并。代价是只留相对顺序、丢掉原始分。
  • Rerank 为什么换 cross-encoder：RRF 只看"名次"，并没真正"读懂"问题和资料内容的关系，精度不够。Rerank 改用 cross-encoder（交叉编码器），把 query 和 chunk 拼到一起逐字比对再打分，能捕捉到细节，所以更准。
  • bi-encoder vs cross-encoder（用个比方）：bi-encoder 像"看简历海选"——每个人把简历（向量）提前做好存起来，来了一个岗位（query）就按相似度排序，快但只看大概，适合海量筛选；cross-encoder 像"面对面面试"——把岗位要求和候选人资料放一起深入交流（逐字交互）再定，准但慢，只能面少量人。
  • 两段式本质：先用 bi-encoder 从百万级快速捞出 50 个，再用 cross-encoder 精排这 50 个选 Top10。就是「初筛 → 面试 → 录用」的三级漏斗——用"快模型粗筛 + 慢模型精读"平衡速度与精度，这也是几乎所有搜索系统通用的思路。
知识图谱通道（LightRAG）能解决什么问题？

一句话：普通检索像"查单页"，图谱像"查关系网"。普通 RAG 把文档切成一段段、各自按相似度找，天然割裂了文档之间的联系，所以答不了"需要跨文档关联、多跳推理"的问题。

  • 它怎么解决：LightRAG 先把文档抽成一张知识图谱（提取"实体"和"实体间的关系"），检索时不再是查片段，而是沿着图上的关系跳着找（多跳遍历）。
  • 能干嘛：项目支持 LightRAG 的五种图检索模式（naive/local/global/hybrid/mix），典型场景是论文引用链——比如"谁引用了某篇论文""A 方法 → B 改进 → C 现状"的研究脉络追踪，这正是普通检索做不到的。
  • 代价（所以要降权）：建图谱要先做实体抽取、关系抽取，成本高、步骤重，而且图谱上的噪声也可能比关键词更高，所以在 RRF 里给它降权、作为补充通道而不是主力。

模块二 · 附：量化效果（简历数据怎么来的）

  • 自建评测集：50 条研发领域评测用例，覆盖向量语义检索 / 关键词精确匹配 / 图谱引用链 / 融合多主题四类通道，基于真实检索日志构造 + 人工抽检。
  • 指标：Recall@10 达 88.6%、MRR 0.72，三路融合较单路向量 Recall@10 提升 12.3%；意图路由 Top-1 准确率 92.5%；流式首包 P50 1.8s。
  • 面试提示：这些数据要能讲清"怎么测出来的"——评测集如何构造、指标如何计算、对比基线是什么，比背数字更重要。
这些指标分别是什么意思？（Recall@K / MRR / Precision@K / Top-1 / 延迟，通俗版）

先统一一个背景：评测时，每条问题都有人工标注的"正确答案"（相关文档 reference）和系统实际召回的结果（retrieved），所有指标都是在比"这两者对得上多少"。下面逐个讲：

  • Recall@K（召回率@K）＝ 88.6%：衡量"该找回来的资料找回来了多少"，越接近 1 说明漏得越少。公式：前 K 个结果里命中的相关文档数 / 总相关文档数。例：一道题相关文档有 5 篇，前 10 个结果命中 4 篇，则 Recall@10 = 4/5 = 0.8。这是 RAG 检索最看重的指标——第一关漏了，后面精排、生成再准也救不回来。
  • MRR（平均倒数排名）＝ 0.72：不仅看"找没找到"，还看第一个正确答案排得够不够靠前。公式：单条 = 1 / 第一个相关文档的位置，再对所有问题取平均。排第 2 名得 1/2=0.5，第 1 名得满分 1.0。0.72 意味着平均第一个正确论文排在 1/0.72 ≈ 1.4 名左右，基本进前三，补足了 Recall 没体现的"排序质量"。
  • Precision@K（精确率@K）：衡量"召回来的结果里有多少是真正相关的"，越接近 1 说明噪音越少。公式：前 K 个里命中的相关数 / K（分母固定为 K）。例：前 10 条里只有 3 条相关，则 Precision@10 = 0.3。它与 Recall 此消彼长（Recall 高易带噪音、Precision 高易漏），所以检索用"粗召回 Top50 → Rerank 精排 Top10"两级漏斗来平衡。
  • Intent Top-1 准确率＝ 92.5%：衡量"意图路由判断得准不准"。取系统打分最高的那个意图叶子节点（Top-1），与人工标注的正确意图比对，一致的占比就是准确率。例：100 条问题里约 92~93 条系统"第一选择"和人工一致。它不是"最终回答准确率"，只衡量分流这一环，这也是它单独列在"问题理解与意图路由"下的原因。
  • P50 / P95 延迟＝ 首包 1.8s：衡量"快不快"。把所有请求耗时从小到大排序：P50（中位数）是正中间那个，P50=1.8s 意味一半请求比它快，代表"典型体验"；P95 是第 95% 那个，代表"最差 5% 的下限"。用 P50 而非平均值是因为延迟分布有长尾，均值会被少数慢请求拉高。这里的首包（TTFT）特指"发出问题到收到第一个字"，流式场景下它决定用户"感觉快不快"。

面试小结：这几个指标要配合看——Recall 高 + MRR 高说明"召回全且排得对"（检索理想状态）；Precision 低说明噪音多，靠 Rerank 精排补；延迟与检索质量是相互平衡的两端（更准往往更慢），用档位 / 缓存 / 并行来折中。

模块二 · 附：arXiv 两级检索（核心创新）

为什么要做"两级检索"？它解决了传统全文入库的什么问题？

先打个比方：图书馆有两套系统——一套是"目录卡片"（薄薄一张，记书名+简介+编号），一套是"借书"（按需去书库取整本原书）。目录适合在海量书里快速定位"是哪本"，借书才真正读内容。两级检索就是同样的道理。

学术论文数据量大（百万级）、单篇正文很长。若把每篇全文都向量化入库，会带来两个麻烦：

  • 索引膨胀：单篇全文数 KB~数十 KB，百万篇全存进去，存储和检索成本直接爆炸。
  • 召回噪音：正文里的公式、参考文献、附录，大多和"论文主题"关系不大，混进去反而会稀释检索的相关性，让结果不准。

所以设计成两级——第一级低成本召回（只存摘要，单篇约 0.2KB） + 第二级高精度精读（按需拉全文）。这是本项目区别于普通知识库问答的核心亮点：

第一级 abstract 全局召回 精确定位候选论文 第二级按需拉 arXiv 全文 局部精读 喂 LLM 生成

  • 第二级：对命中论文按需拉取 arXiv 全文，局部精读后再喂 LLM，回答真正的技术细节（摘要里没有的实现细节）。
用一个真实案例走一遍完整闭环？

假设用户问："帮我精读《A Survey on Knowledge-Oriented Retrieval-Augmented Generation》这篇论文的技术实现细节"，系统内部是这样走的：

  1. 意图识别：Query 经 LLM 打分，命中了两个意图节点——paper（KB 召回节点）和 paper-detail（MCP 精读节点），判定为"既要检索论文、又要精读技术细节"。
  2. 第一级召回：paper 节点驱动向量检索，在学术库 paperarxivstore 里召回摘要，Top 结果里带出该论文的元信息 arxiv_id: 2503.10677（标题也完全对上）。
  3. 两级衔接：这段命中摘要（含 arxiv_id）作为「命中上下文」注入 MCP 工具 arxiv_fetch_fulltext 的参数提取，LLM 从中抽取出 arxivId = "2503.10677"——用户全程没有手输编号。
  4. 第二级精读：MCP 工具用 2503.10677 实时拉取 arXiv 全文（HTML5 版，约 15 万字），清洗公式与章节结构，分段精读。
  5. 生成回答：LLM 基于全文生成带引用的技术细节回答——这些细节是摘要里根本没有的（如具体方法框架、实验设置、评估指标）。

这个案例里，两级检索的价值一目了然：如果只做摘要问答，第 5 步的"技术实现细节"根本答不出来；如果全文全部入库，23 万篇论文的存储成本又不可承受。两级检索正好各取所需。

两级之间的衔接是怎么做的？（关键，面试必问）

先说难点：要拉全文，工具必须有论文编号 arxivId，可用户通常只说"那篇论文"，根本不会报编号。所以衔接的关键就是——让系统自己"顺藤摸瓜"把编号挖出来。

  • 第一级命中的摘要里自带 arxiv_id，把它作为「命中上下文」，注入第二级 MCP 工具的参数提取阶段。
  • 核心方法 McpParameterExtractor.extractParametersWithContext(question, tool, paramPrompt, hitContext)：让 LLM 从「用户问题 + 命中摘要」一起提取 arxivId，而不是只从用户那句问话里硬找。
  • 为什么必须这么做：arxivId 是必填参数，如果不把命中上下文喂进去，LLM 提取不到编号，就会走「澄清」分支让用户手输——体验很糟、工具也调不起来。
  • 踩过的坑：早期在参数提取的 prompt 里写了一个具体编号当示例，结果 LLM 照抄示例编号、而不是从命中上下文提取真实编号。修复：移除示例值 + 强化"必须从命中资料实际内容提取、禁止沿用示例/编造编号"的约束。
  • 兜底：MCP 精读节点本身也绑定了学术库 collection，即使 KB 召回节点没单独命中，也能驱动学术库召回，保证命中上下文里总能有 arxiv_id 的来源。
两级检索 vs 传统全文入库，量化对比？
维度全文全部入库（传统）abstract 召回 + 按需拉全文（两级）
索引成本高：全文向量化、存储膨胀低：只索引摘要（单篇约 0.2KB），万篇毫秒级召回
召回噪音高：公式/参考文献混入干扰低：摘要聚焦核心，定位精准
精读深度中：命中片段未必是关键段高：按需拉全文，精读具体技术细节
覆盖范围受本地入库 PDF 限制广：摘要覆盖百万级，全文按需实时拉取

模块三 · 模型工程化与 Agent 编排（简历句③：多供应商客户端 + 熔断降级 + MCP/ReAct）

服务端工程化怎么落地？（Java + Spring Boot）
  • MyBatis-Plus 持久层：管理知识文档、分块、意图节点、对话等元数据，内置通用 CRUD + 条件构造器 + 分页。
  • Redis 缓存：意图树、意图分类结果、模型健康状态等热点数据缓存，降低重复计算；并用 ZSET + Lua 实现公平排队限流。
  • RocketMQ 异步入库：文档入库/分块/删除这类重活丢到消息队列异步处理，配合事务消息 + 幂等保证不重不漏，避免阻塞检索主链路。
多供应商模型客户端如何抽象？
  • 抽象了 ChatClient / EmbeddingClient / RerankClient / VlmClient 统一接口，屏蔽不同供应商（OpenAI 系、通义、DeepSeek 等）的差异。
  • 模型档位（tier）：把模型按能力/成本分层（如基础档、增强档），不同场景（意图识别、重写、生成、摘要）选用不同档位，控制成本。
  • 多候选路由：同一档位配置多个候选模型，自动切换。
  • 新供应商只需实现对应接口并加入候选配置，即可复用首包探测、健康检查、熔断降级全套机制（策略模式 + 配置驱动）。
三态熔断降级是怎么实现的？（高频追问）

★ 通俗版：可以把它想成一个"智能接线总机 + 多个备用客服"的场景。总机知道每个客服（模型）的健康状况，按下面三条规则办事：

  • 平时正常（CLOSED）：来电话（请求）正常接转。但只要某个客服连续接二连三地出错（达到 failureThreshold），总机就判定"这个客服今天不行了"，把 TA 临时停掉（OPEN），不再给它派活，免得用户一直听到"占线/出错"。
  • 停掉一段时间后试探（HALF_OPEN）：停了一阵（openDurationMs 到期）后，总机偷偷只放一个电话进去试探——这次能接通（成功）就恢复上岗（回 CLOSED）；还是不行就再停掉（回 OPEN）。
  • 关键细节：同一时刻只允许一个试探电话，防止故障刚恢复就涌进一堆请求把客服再次压垮（防雪崩）；试探失败会自动切换到下一个备用客服，用户全程几乎无感知。

★ 专业版：核心类 ModelHealthStore 用 ConcurrentHashMap 给每个模型维护健康状态，实现标准断路器（Circuit Breaker）三态模型：

  • CLOSED（关闭）：正常放行，记录连续失败次数 consecutiveFailures，达到 failureThreshold 后切换为 OPEN。
  • OPEN（打开）：直接拒绝调用（快速失败），持续 openDurationMs 时间，避免持续打已故障的模型。
  • HALF_OPEN（半开）：OPEN 超时后，只放行一个探测请求（探测名额 halfOpenInFlight + 令牌 halfOpenToken），成功回 CLOSED，失败再回 OPEN。
  • 并发安全：用 ConcurrentHashMap.compute() 原子更新状态；allowCall() 发放许可（被熔断/探测在途返回 null 即拒绝），markSuccess()/markFailure() 更新健康，releaseHalfOpenPermit() 只释放自己令牌持有的探测名额，保证同一时刻只有一个探测请求，防"雪崩式探测"。
  • 降级本质：普通 RPC 熔断降级是"返回默认值"，这里AI 模型熔断的降级是"切到下一个候选模型"——ModelSelector 先把不可用模型筛出候选，ModelRoutingExecutor 遍历候选逐个尝试，失败即 markFailure 并继续下一个。
  • 配合首包探测（流式场景下首包超时/空响应/异常即触发降级并切换）和多候选自动切换，形成完整容错链路。
Agent 编排与"带逐句引用的文献综述"怎么实现？
  • 通过 MCP 协议对接 Semantic Scholar 做论文搜索与引用分析（search / citations / references），精读全文时经其 externalIds 映射到 arXiv 拉取全文，并支持工具发现、参数提取、Schema 校验（注册表模式管理工具）。
  • 文献综述生成是多步骤编排（检索 → 分组 → 引用分析 → 综合），每一步产出给下一步，最终生成逐句带引用的综述。
  • 引用编号机制（核心）：上下文格式化阶段只写入内部锚点 data-ragent-doc-id，来源装配完成后由 CitationContextEnricher 依据 SourceRef.index 替换为模型可见的 ref 编号。
  • 关键设计：Prompt、SSE、落库、前端复用同一份来源编号，同时不把内部文档 ID 暴露给模型（安全 + 一致性）。引用开关关闭时只抹掉内部锚点、不注入编号，但都要过这一道，防止 docId 漏进模型可见文本。
流式首包 P50 1.8s 是怎么达到的？
  • 多路并行召回：四通道 CompletableFuture 并行，而非串行等待，显著缩短检索耗时。
  • SSE 流式输出：首包即"第一个字"，决定用户"感觉快不快"，用事件回调边生成边推。
  • 模型档位选择：意图/重写等用低档位快模型，只把生成主链路留给高档位，平衡速度与成本。
  • 缓存命中：意图树、意图分类结果等热点数据走 Redis 缓存，降低重复计算。
  • P50 而非均值：延迟分布有长尾，均值会被少数慢请求拉高，P50（中位数）更能代表典型用户体验。

模块三 · 附：工程保障（并发 / 消息 / 可观测）

Redis 公平排队限流怎么实现？
  • 用 Redis ZSET 做公平排队：每个请求入队时写入时间戳作为 score，按 先进先出（公平）原则出队。
  • 配合 Lua 脚本做原子抢占（判断许可 + 出队一个原子操作），避免并发下超发。
  • 用过期信号量（key 带 TTL）避免请求宕机导致的许可泄漏，用 Pub/Sub 唤醒等待队列，支持进度、超时、取消与许可回收。
  • 解决的核心问题：突发流量压垮模型服务（模型推理慢、成本高），用排队削峰而非直接拒绝。
RocketMQ 事务消息与幂等怎么落地？
  • 事务消息解决"本地事务与发消息"的一致性：异步入库时先发半消息，执行本地事务，再根据结果 Commit/Rollback，保证分块与删除任务不重不漏。
  • 幂等：因为 MQ 是"至少一次"投递，消费者需要幂等处理（唯一键去重、状态机判断），防止重复入库。
  • 远程刷新文档用分布式锁 + 状态机控制，避免并发刷新冲突。
全链路 Trace（@RagTraceNode + AOP）怎么实现？
  • 自定义注解 @RagTraceNode(name, type) 标注关键节点（如 multi-channel-retrieval、intent-resolve），通过 AOP 切面在方法前后自动记录耗时、输入输出、异常。
  • 一次问答形成 Trace Run → 多个 Trace Node 的树状结构，管理端可查看趋势、详情。
  • 上下文透传：用 TTL（ThreadLocal 增强）保证用户上下文和 Trace 上下文能在 CompletableFuture 跨线程池传递（因为并行检索/意图识别都会切换线程）。
  • 价值：RAG 链路长、环节多，出问题能精确定位到哪一步（是召回少还是模型慢还是融合错）。
会话记忆（最近 N 轮 + 持久化摘要）怎么控制 Token 成本？
  • 最近 N 轮消息：只保留最近的对话轮次直接拼入 prompt，避免无限增长。
  • 持久化摘要：更早的历史消息用 LLM 压缩成摘要持久化保存，用摘要代替原文，既保留关键上下文又省 Token。
  • 两者结合，在"上下文完整度"和"Token 成本"之间取平衡。

二、从简历出发的项目追问（模拟面试官）

🎯 说明：以下每个问题都直接对应简历上的一句话，面试官大概率会揪着这些点追问。括号里标注了"简历原文"和"回答要点"，训练目标是"简历每个字都能展开讲 3 分钟"。
简历写"四通道并行召回 + RRF 融合"，那为什么要多路召回？单路向量到底哪里不行？
  • 向量检索基于语义相似度，擅长"意思相近"，但对精确关键词、专有名词、缩写、数字不敏感，可能语义漂移或漏召回（如"ResNet-50"这类编号、或某个精确论文标题）。
  • 关键词（BM25）擅长精确匹配但不懂语义，同义替换就召回不到。
  • 知识图谱擅长多跳关系推理（引用链、方法演进）。联网搜索补时效。
  • 四者互补，融合后召回率显著提升——这是实测 12.3% 提升的根因。
简历说"RRF 加权融合"，RRF 公式是什么？为什么用排名而不是分数融合？加权怎么定权重？
  • 公式 Σ 1/(k+rank)，k 通常取 60。用排名而非原始分数，是因为不同通道分数量纲不同（向量是余弦分、BM25 是相关分，不可直接比），用排名天然归一化。
  • 加权：不同通道可信度不同（图谱全局图噪声高），所以加 weight 降权，避免噪声通道抢前排。
  • 追问可能延伸到：RRF 的缺点（只用排名、丢原始分数）→ 怎么补？答：融合后再接 Rerank（cross-encoder）精排，重新引入语义交互。
"并行召回用 CompletableFuture"，线程池参数怎么配的？为什么用 orTimeout 而不是 cancel？
  • 线程池参数（corePoolSize / maximumPoolSize / keepAliveTime / workQueue / 拒绝策略），检索是 IO 密集，核心线程数按 CPU 核数 × 2 左右 + 合理队列。
  • orTimeout 不 cancel：超时后只是放弃该路结果，任务继续在池里跑完。原因是 orTimeout 不中断底层线程，避免 cancel 引发的资源未释放和线程中断副作用；且"最慢一条"不应钳制其他通道融合。
  • 追问：为什么不用 get(timeout)？因为 get 会阻塞主线程，而 orTimeout 是异步非阻塞。
简历写"LLM 打分 + 树形结构意图识别"，为什么不用关键词规则而用 LLM 打分？树形结构有什么好处？
  • 规则/关键词只能覆盖显式词面，无法理解语义和隐式意图（"最近 CV 有什么新进展"没有显式提到"计算机视觉"）。LLM 打分能理解语义，Top-1 准确率 92.5%。
  • 树形「学科→方向→子方向」层级，能做由粗到细的渐进路由，也便于管理和扩展（新增子方向只需加叶子节点）。
  • 追问：LLM 打分有延迟/成本怎么办？答：意图分类用低档位模型（模型档位控制成本），且并行执行，失败降级为空意图。
简历写"多候选路由 + 熔断降级"，三态熔断和常见的 Hystrix/Resilience4j 有什么区别？为什么自己实现？
  • 核心就是标准断路器三态（CLOSED/OPEN/HALF_OPEN），逻辑和 Resilience4j 一致。
  • 自己实现的理由：① 熔断对象是AI 模型而非普通 RPC，降级策略是"切换候选模型"而非"返回默认值"；② 需要和首包探测、模型档位深度耦合，通用库不够贴合；③ 用 ConcurrentHashMap.compute 原子更新，轻量无外部依赖。
  • 追问：半开状态为什么只放一个探测请求？答：防止故障恢复瞬间被大量请求"雪崩式"打崩，用 halfOpenInFlight 令牌保证同一时刻只有一个探测。
简历写"最近 N 轮消息 + 持久化摘要控制 Token 成本"，为什么不全量保留？摘要会不会丢关键信息？
  • 全量保留会导致 prompt 无限膨胀，Token 成本线性增长且可能超模型上下文窗口。
  • 折中：近期消息保留原文（细节全），远期历史压缩成摘要（保留关键结论）。
  • 摘要确实可能丢细节，所以是权衡——也可以说这是"最近 N 轮 + 摘要"而非"纯摘要"，近期细节不丢。
简历写"自建 50 条评测集，Recall@10 88.6%"，评测集怎么构建的？Recall@10、MRR 怎么算？怎么保证评测可信？
  • 基于真实检索日志构造（真实用户查询），再人工抽检标注相关文档，避免纯合成数据的偏差。
  • Recall@10 = 前 10 个结果命中相关文档的比例；MRR = 相关文档出现位置倒数的平均（1/rank）。
  • 可信度：真实日志 + 人工标注 + 固定基线对比（单路 vs 三路融合），能复现 12.3% 的提升。
  • 追问：为什么用 Recall 而不是 Precision？答：RAG 检索阶段更看重"别漏掉相关文档"（召回优先），精排阶段再保证准确。
简历写"流式首包 P50 1.8s"，首包延迟怎么优化？P50 为什么比平均值更有意义？
  • 优化手段：多路并行召回（而不是串行）、SSE 流式输出、模型档位选择、缓存命中。
  • P50（中位数）比均值更能反映"典型用户体验"，因为延迟分布通常有长尾，平均值会被少数慢请求拉高。
  • 追问可能延伸到 P95/P99，以及首包（TTFT）和总时延的区别——首包决定"感觉快不快"，流式下用户更敏感首包。
简历写"MCP 对接 Semantic Scholar，ReAct 编排生成文献综述"，MCP 是什么？和普通 function calling 有什么区别？ReAct 是什么？
  • MCP（Model Context Protocol）：模型上下文协议，标准化"模型调用外部工具"的接口，类似 AI 界的"USB 接口"。核心是工具发现 + 统一调用 + Schema 校验，工具可远程部署、动态发现，而传统 function calling 是应用内硬编码函数。
  • ReAct（Reasoning + Acting）：让模型交替进行"推理（Thought）→ 行动（Action）→ 观察（Observation）"，用工具结果修正推理，适合多步任务（如文献综述的检索→分组→引用分析→综合）。
  • 口径统一（以简历为准）：简历口径 = MCP 对接 Semantic Scholar 做论文搜索与引用分析，精读全文时通过它映射到 arXiv 拉全文。面试统一按此说法讲，不再提 arXiv 直连 / You.com。技术衔接点：Semantic Scholar 的 externalIds 字段能返回 arxiv_id，据此映射到 arXiv 拉全文，正好和「两级精读」闭环接上。若被追问 Semantic Scholar API，答：官方 Graph API（api.semanticscholar.org/graph/v1），搜索用 paper/search，引用用 citations/references，需带 API key。
  • 追问：MCP 和 function calling 选型？答：MCP 解耦了工具实现和模型，工具可以跨模型复用、远程部署，工程上更灵活。
简历写"Redis ZSET + Lua 公平排队限流"，为什么要公平排队而不是令牌桶？Lua 脚本解决什么问题？
  • 令牌桶/漏桶是"限速"，但突发时要么拒绝要么丢弃；公平排队是削峰填谷——模型推理慢，与其拒绝不如排队等待，保证公平（先进先出）不饥饿。
  • Lua 脚本：判断许可 + 出队是一个复合操作，若拆成多次 Redis 命令会有并发竞态（超发），Lua 脚本在 Redis 内原子执行，保证线程安全。
  • 追问：为什么用 ZSET？答：ZSET 以时间戳为 score，天然支持按时间排序（公平队列），且支持超时清理。
简历写"两级精读（仅索引摘要，单篇约 0.2KB）"，为什么不把全文入库？两级精读解决什么问题？两级之间怎么衔接？
  • 为什么不全量入库：论文全文数 KB~数十 KB，百万篇全文向量化会导致索引膨胀（存储/检索成本爆炸）+ 召回噪音（公式、参考文献、附录稀释主题相关性）。只索引摘要，单篇约 0.2KB，成本低、定位准。
  • 两级设计：第一级摘要全局召回定位「是哪几篇论文」→ 第二级按需调 arxiv_fetch_fulltext 拉全文精读「具体技术细节」。本质是把「索引成本」和「精读精度」解耦，像图书馆「书目检索 + 借阅原书」。
  • 两级衔接（必问）：第一级召回摘要里带 arxiv_id，作为「命中上下文」注入第二级 MCP 工具的参数提取，让 LLM 自动抽出 arxivId——用户全程不用手输编号。
  • 踩坑：参数提取 prompt 里写了具体编号示例，LLM 会照抄示例而不从命中上下文提取真实编号，修复是移除示例值 + 强化「必须从命中资料实际提取、禁止编造」。
简历说"通用研发知识检索平台"，知识库是怎么分库的？为什么按功能分层而不是按学科切？多库之间怎么路由？
  • 分库原则：按「检索方式/数据形态」分，不按学科分。落地为两个逻辑库——学术摘要库 paperarxivstore + 内部文档库 internal_docs（共享物理向量库，靠 collection_name 区分），图谱和联网是独立检索通道。
  • 为什么功能分层为主：学科切分有边界模糊（"多模态 RAG"算 CV 还是 NLP？）、数量爆炸（arXiv 几十类）的问题，且学科路由意图树已经做了，库级再切是重复。
  • 学科怎么处理：学科类别做成结构化元数据字段（category），检索时标量过滤（metadata["category"] == "cs.CL"），而不是拆库。
  • 多库路由：意图树节点通过 collection_names 绑定库，命中 paper 走学术库、命中 internal-tech 走内部库；多个子问题分别定向，才体现「定向 vs 全局」的价值。
  • 平台化叙事：同一套多路检索 + 两级精读引擎，既能查 arXiv 论文，也能接企业私有文档，这才是「通用」二字的真义，不是只能查论文的 demo。

三、对应八股专题

📚 说明：以下是项目背后必考的八股，按"RAG / 后端 / 数据库"三大块组织。这些是基础，面试官可能从项目细节自然过渡到这些基础问题。

3.1 RAG 与检索

RAG 是什么？为什么需要？和微调的区别？
  • RAG：生成前先从外部知识库检索相关内容拼进 prompt 再生成，得到更准确、可溯源、能跟上最新知识的回答。
  • 为什么：LLM 知识有截止、会幻觉、无法访问私有数据；RAG 用外部知识弥补且能给出引用来源。
  • 对比微调：RAG 灵活、实时更新、可溯源；微调把知识写进参数，适合固化风格/能力，两者可结合。
向量检索原理？Embedding 是什么？Milvus 常用索引？
  • Embedding：文本映射成高维稠密向量，语义相近距离近（余弦/内积）。
  • 向量检索：query 也嵌入成向量，在库里找最近邻（ANN，高维精确搜索太慢）。
  • 索引：HNSW（图，查询快召回高，内存大）、IVF（聚类倒排，省内存召回略低）、PQ（乘积量化压缩，省内存有损）。
为什么选 Milvus 做向量库？它解决了什么问题？
  • Milvus 是什么：专用向量数据库，分布式、支持亿级向量、索引类型丰富（HNSW/IVF/PQ/量化），标量过滤与向量检索原生融合（metadata["key"] == "value"）。
  • 选它的理由：落地场景是 arXiv 170 万+ 论文，数据规模逼近百万级且持续增长，需要亿级扩展能力 + 原生标量过滤 + 独立伸缩，匹配「通用研发知识检索平台」的长期定位。
  • 标量过滤的价值：多知识库靠 collection_name 区分、学科靠 metadata["category"] 过滤，Milvus 的标量过滤和向量检索能在一次查询里 AND 组合，避免"先查向量再回表过滤"的二次往返。
  • 接口抽象：检索接口（VectorStoreService / VectorRetrieverService）已抽象，向量库只作为可替换的实现——这正是「业务编排 / AI 供应商差异 / 基础设施」分层隔离的价值体现。
多知识库路由是怎么做的？元数据标量过滤是什么？
  • 多库的物理实现：多个逻辑库共享同一个物理向量表，靠 collection_name 标量字段区分，检索时 WHERE collection_name IN (...) 过滤。
  • 路由：意图树节点通过 collection_names（JSONB 数组）绑定目标库，命中意图后定向到对应库；高置信度走定向检索，否则全局检索 + 补充路兜底。
  • 元数据标量过滤：文档入库时把 category 等属性作为 metadata 写进向量行，检索时 metadata->>'category' = 'cs.CL' 做等值过滤，与向量相似度、collection 过滤 AND 组合。
  • 为什么学科用字段不用库：一篇论文多标签、跨学科，物理拆库会有归属难题；字段过滤天然支持多标签与跨学科，且和意图树的学科路由不重复。
BM25 原理？为什么关键词检索仍必要？
  • BM25 是 TF-IDF 改进版，考虑词频 TF、逆文档频率 IDF、文档长度归一化。
  • TF 有饱和（非线性增长），IDF 惩罚常见词，长度归一化防长文档占便宜。
  • 对专有名词、编号、缩写、精确术语这类向量模型可能没见过的词，关键词更可靠。
GraphRAG / LightRAG 和普通 RAG 的区别？
  • 普通 RAG 切块后按相似度检索，割裂文档间关系，无法多跳推理。
  • GraphRAG 先抽实体+关系成图谱，检索时利用图结构多跳遍历，能答"实体 A 和 C 什么关系"。
  • 代价：图谱构建（抽取）成本高。
Rerank 是什么？bi-encoder 和 cross-encoder 区别？
  • Rerank：对召回候选（如 Top100）精细排序，选出真正最相关的 Top 几条给 LLM。
  • bi-encoder（双塔）：query 和文档独立编码再算相似度，快（可预存）、但无交互、精度低，适合召回。
  • cross-encoder（交叉）：query+文档拼一起充分交互再打分，精度高但慢、无法预存，适合精排。
  • 经典架构：bi-encoder 快速召回海量候选，cross-encoder 精排少量候选。
分块（chunking）策略？Recall@K、MRR、NDCG 含义？
  • 分块：固定长度、按段落/标题结构化、语义分块（按语义边界）、父子块。太大信息稀释、太小上下文割裂。
  • Recall@K：前 K 命中相关文档比例（"该找的找回来没"）。
  • MRR：相关文档位置倒数的平均（"第一个对的排多靠前"）。
  • NDCG：考虑位置权重 + 相关度分级的排序质量。
两级检索（摘要召回 + 全文精读）的八股：为什么要这么设计？
  • 本质：在「索引成本」和「精读精度」之间解耦。第一级只索引轻量摘要（标题+摘要+arxiv_id），成本极低、覆盖面广；第二级按需拉全文，精度高、按需付费。
  • 对比全文入库：全文入库 = 索引膨胀 + 召回噪音（公式/参考文献稀释相关性）；两级检索 = 摘要定位 + 全文精读，各取所长。
  • 类比：像图书馆的「书目检索 + 借阅原书」——先查目录定位是哪本书，再借出来精读，而不是把所有书的正文都复印一份堆在检索区。
  • 适用边界：适合「文档大、数量多、正文不适合整段入库」的场景（论文、专利、法典）；不适用于「短文本、需要全文逐字匹配」的场景。
两级之间的衔接（召回结果 → 工具参数）怎么做？踩过什么坑？
  • 做法：第一级召回摘要含 arxiv_id，作为「命中上下文」注入第二级 MCP 工具的参数提取，让 LLM 自动提取 arxivId，而非要求用户手输。
  • 为什么必须：用户只问"某论文细节"，不给编号；而 arxivId 是必填，不注入上下文就会走「澄清」、工具调不起来。
  • 坑：参数提取 prompt 里写具体编号示例，LLM 会照抄示例而非从命中上下文提取真实编号——解法是移除示例值 + 强化"必须从命中资料实际提取、禁止编造"。
  • 兜底：精读节点也绑定学术库 collection，即使 KB 召回节点未单独命中，也能驱动学术库召回，保证命中上下文有 arxiv_id 来源。
MCP（Model Context Protocol）是什么？和 function calling 的区别？
  • MCP：模型上下文协议，标准化「模型调用外部工具」的接口（工具发现 + 统一调用 + Schema 校验），类似 AI 界的 "USB 接口"。
  • 核心区别：MCP 工具可远程部署、动态发现、跨模型复用（如 Semantic Scholar 数据源部署在独立 mcp-server，任意 Agent 都能连），而传统 function calling 是应用内硬编码函数。
  • 项目里的落地：mcp-server 独立服务封装 Semantic Scholar 搜索与引用分析工具，bootstrap 通过 McpClientAutoConfiguration 连 9099 端口自动注册；精读全文时经 externalIds 映射到 arXiv 拉取，意图路由到 paper-detail 节点时触发调用。
意图分类器的 examples 怎么设计？踩过什么坑？（真实案例）
  • 原理：意图节点用 examples（示例问题列表）做向量化匹配，LLM 对用户问题打分，超过阈值（如 0.35）才命中该节点。
  • 真实翻车案例：用户问「详细介绍下这篇论文：GraphRAG 与上下文优化」，结果只命中了 paper（KB 召回节点），paper-detail（MCP 精读节点）没被触发，最后走澄清分支让用户手输 arXiv 编号。
  • 根因：paper-detail 的 examples 只有「技术方案怎么实现」「模型结构」「算法流程」这类专业表述，没有「详细介绍」「详细讲」「深入讲」这类用户口语化表达——分类器识别不出"详细介绍"也是精读意图。
  • 修复：把 examples 从 8 条扩展到 14 条，补充「详细介绍下这篇论文」「详细讲一下」「深入讲讲」「展开讲讲」「帮我看看全文」等泛化表达，覆盖用户真实问法。
  • 经验教训：意图 examples 必须覆盖用户真实的口语表达，而不是只写"标准术语"。同一个意图（精读）可以有多种问法，examples 越贴近真实用户、鲁棒性越强。

3.2 Java 后端与工程化

Spring 的 IoC 和 AOP 是什么？AOP 代理方式？
  • IoC：对象创建和依赖注入交给容器管理，通过 @Autowired/构造器注入降低耦合，核心是 Bean 容器。
  • AOP：把横切关注点（日志、事务、埋点）从业务抽出，通过代理在方法前后织入。项目用 @RagTraceNode + AOP 做全链路 Trace。
  • 代理：JDK 动态代理（基于接口）、CGLIB（基于子类继承）。
CompletableFuture 原理？线程池 7 参数？拒绝策略？
  • CompletableFuture：Java 8 异步编排工具，支持 thenCombine/allOf/anyOf 组合和回调。
  • 线程池 7 参数：corePoolSize、maximumPoolSize、keepAliveTime、unit、workQueue、threadFactory、RejectedExecutionHandler。
  • 拒绝策略：AbortPolicy（抛异常）、CallerRunsPolicy（调用者执行）、DiscardPolicy（丢弃）、DiscardOldestPolicy（丢弃最旧）。
RocketMQ 如何保证消息可靠？事务消息和幂等？
  • 可靠性三环节：生产端（同步+确认+重试）、Broker 端（持久化+主从）、消费端（手动 ACK+失败重试）。
  • 事务消息：先发半消息→执行本地事务→Commit/Rollback，半消息消费者不可见，解决本地事务与发消息一致性问题。
  • 幂等：至少一次投递会重复，需唯一键去重/状态机判断。
MyBatis-Plus 和 MyBatis 区别？
  • MyBatis：半自动 ORM，手写 SQL，灵活但样板多。
  • MyBatis-Plus：增强版，内置通用 CRUD（BaseMapper）、条件构造器（Wrapper）、分页、逻辑删除，同时保留手写 SQL。

3.3 数据库（MySQL / Redis）

MySQL 为什么用 B+ 树？最左前缀、覆盖索引、索引失效？
  • B+ 树矮胖（多叉、层少）减少 IO；叶子有序链表范围查询快。对比 B 树：非叶子不存数据、查询稳定；对比哈希：只能等值查询。
  • 最左前缀：联合索引 (a,b,c) 只有从 a 开始才命中（a、a+b、a+b+c）。
  • 覆盖索引：查询列全在索引里，不回表。
  • 失效：对索引列做函数/运算、隐式类型转换、like '%xx'、or 连接非索引列、不满足最左前缀。
ACID、四种隔离级别、MVCC 原理？
  • ACID：原子性、一致性、隔离性、持久性。
  • 隔离级别：读未提交（脏读）、读已提交（不可重复读）、可重复读（幻读，InnoDB 用 Next-Key Lock 基本解决）、串行化。
  • MVCC：undo log 版本链 + Read View，每行有事务 ID 和回滚指针，读写不阻塞，实现快照读。
行锁、表锁、间隙锁、Next-Key Lock 区别？
  • 行锁：锁单行，并发高。表锁：锁整表，并发低。
  • 间隙锁（Gap）：锁索引记录间空隙，防幻读插入。
  • Next-Key Lock：行锁 + 间隙锁组合，InnoDB 可重复读下默认加锁方式。
  • 乐观锁（版本号/CAS）vs 悲观锁（直接加锁）。
redo log、binlog、undo log 区别？两阶段提交？
  • redo log：InnoDB 层，物理修改，崩溃恢复（持久性），WAL。
  • binlog：Server 层，逻辑操作，主从复制、数据恢复。
  • undo log：旧值，事务回滚 + MVCC。
  • 两阶段提交（2PC）：保证 redo 和 binlog 一致——先 redo prepare，再写 binlog，最后 redo commit。
Redis 五种数据类型底层结构？
  • String：SDS。List：quicklist（ziplist+双向链表）。Hash：ziplist/hashtable。Set：intset/hashtable。
  • ZSet：ziplist 或 skiplist + dict，跳表支持范围查询和排名 O(logN)。限流用 ZSET 做公平队列。
缓存穿透、击穿、雪崩的区别和解决？
  • 穿透：查不存在的数据。解决：缓存空值、布隆过滤器、参数校验。
  • 击穿：热点 key 过期瞬间大量打到 DB。解决：互斥锁/分布式锁、热点 key 永不过期、续期。
  • 雪崩：大量 key 同时过期或 Redis 宕机。解决：过期时间加随机、多级缓存、限流降级、高可用。
  • 口诀：穿透→布隆/空值；击穿→锁；雪崩→随机过期+高可用。
Redis 持久化 RDB vs AOF？过期删除和淘汰策略？
  • RDB：定时快照，文件小恢复快，可能丢最后快照后数据。
  • AOF：追加写命令，更安全（可每秒 fsync），文件大恢复慢，可混合。
  • 过期删除：惰性删除（访问时查）+ 定期删除（定时抽检）。
  • 淘汰：noeviction、allkeys-lru/lfu、volatile-lru/lfu、random、volatile-ttl。
  • 分布式锁：SET key value NX PX，注意锁续期（看门狗）和误删（唯一 value + Lua 释放）。
