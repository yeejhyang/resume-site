一、Agent 基础与编排

Agent 是什么？三要素？
  • 让 LLM 具备"感知 → 规划 → 行动"，能调工具、观察结果、再决策的自主循环。
  • 三要素：模型（大脑）+ 工具（手）+ 记忆（上下文）。
ReAct 范式？为什么适合 Agent？
  • Reasoning + Acting 交替：Thought → Action → Observation 循环，直到结论。
  • 结合纯 CoT（只推理）和纯 Act（只行动），能边想边做、根据反馈修正，适合查资料/执行代码/多步操作。
多智能体协作 vs 单主 Agent？怎么选？
  • 多智能体：职责清晰、可并行，但跨 Agent 上下文丢失、重复探索、token 叠加。
  • 单主 Agent：自持完整上下文，子代理降级为工具，消除传递损耗、避免重复。
  • 选择依据：任务是否强依赖共享上下文、是否可天然并行。你的 CodeForge 从多级委托改单主 Agent，端到端时长 -38%。
Function Calling 原理？模型怎么"调工具"？
  • 工具描述成 JSON Schema 传给模型，模型输出结构化调用指令。
  • 程序解析 → 执行真实函数 → 结果拼回上下文 → 模型继续。
  • 模型本身不执行代码，只请求调用，由外部执行（安全边界）。
Python 和 Java 在 Agent 开发中各自的优势？
  • Python：AI 生态第一语言，LangChain/LangGraph/PyTorch/向量库都原生支持；动态类型、胶水代码少，做 prompt 编排、工具接入、快速原型迭代最快。
  • Java：强类型 + 成熟并发（线程池/CompletableFuture）+ 稳定企业级框架（Spring Boot），适合承载 Agent 背后的高并发服务、多路召回并行、消息队列、事务等生产级工程底座。
  • 常见分工：Python 写 Agent 核心编排与推理，Java 做后端服务/检索/存储，通过 HTTP/SSE 或 MCP 对接——你的检索平台正是 Java 后端 + 多路召回并行，与 Agent 层解耦。

二、上下文管理与记忆

三级上下文压缩？
  • ① 历史消息裁剪（含工具调用配对修复）；② 工具结果零成本摘要；③ 长会话阈值触发 LLM 摘要降维。
  • 配合统一 token 预算 + 状态机恢复保障断流续跑。
为什么上下文管理重要？Lost in the Middle？
  • 成本（token 越多越贵越慢）、质量（长文本中段信息利用差，即 Lost in the Middle）、稳定性（超窗截断导致失败）。
  • 目标：信息不丢前提下压缩上下文，平衡三者。
短期 vs 长期记忆？
  • 短期：当前窗口内历史，直接拼 prompt，受窗口限制。
  • 长期：跨会话持久化，用向量库检索、摘要记忆、知识库实现。
什么是三层记忆？Agent 中如何实现？
  • 工作记忆（Working）：当前任务窗口内的临时状态、中间步骤、工具结果。实现：上下文消息列表 + 状态机（如 LangGraph State），受窗口/token 预算限制。
  • 情景记忆（Episodic）：跨会话的"发生过什么事"，如用户偏好、历史交互。实现：向量库按语义检索相关经历 + 结构化存储（用户画像、会话摘要）。
  • 语义记忆（Semantic）：稳定的知识/事实/规则，长期不变。实现：RAG 知识库、知识图谱、系统 prompt 里的固定规则。
  • 落地要点：工作记忆靠上下文压缩控预算；情景/语义靠检索按需注入，避免全量塞进 prompt。

三、协议与框架

SSE 是什么？为什么流式用 SSE？
  • 基于 HTTP 的单向服务器推送。LLM 逐 token 生成，SSE 边生成边推、体验好。
  • vs WebSocket：WS 双向全双工，LLM 流式主要是单向，SSE 更轻量、基于 HTTP。
  • vs 轮询：轮询反复请求、延迟高；SSE 服务端主动推、实时。
MCP 协议？和 Function Calling 区别？
  • MCP：标准化"模型 ↔ 工具"的连接协议，像 USB-C 统一外设，解决工具对接碎片化。
  • Function Calling 是模型厂商内部机制；MCP 是跨模型跨工具的通用标准，一个 Server 多客户端复用。
  • 角色：Host（宿主）、Client（发起连接）、Server（提供工具/资源）。
LangChain 是什么？LangGraph 是什么？区别？
  • LangChain：搭建 LLM 应用的组件框架，把 Prompt 模板、模型、工具、记忆、检索器封装成可复用组件，用 Chain/LCEL 串成流水线。适合线性、单向的简单流程（问答、总结、单次 RAG）。局限：Chain 本质是有向无环，难表达循环/回退。
  • LangGraph：建立在 LangChain 之上的有状态、有循环的图编排引擎。核心是 State（共享状态） + Node（节点） + Edge（边，含条件边），支持循环/分支/回退/并行，配合 Checkpoint 断点续跑、人工介入。适合复杂多步 Agent、多智能体。
  • StateGraph：LangGraph 里共享状态贯穿节点的工作流图，表达多步、可回退、可循环。
  • 一句话：LangChain 是"流水线"（直线拼装），LangGraph 是"流程图 + 状态机"（可绕圈、回头、分岔）。
通俗版：怎么理解 LangChain 和 LangGraph？
  • LangChain = 乐高积木：一盒现成零件（提示词、模型、工具、记忆），你只需把它们按顺序拼成一条直线，像流水线 `问题→查资料→喂模型→出答案`。
  • LangGraph = 地图导航：不再是直线，而是一张能来回走、绕圈、分岔的路线图——走到路口按结果决定去向，走错了原路返回，还能同时走几条路、走到一半存档下次继续。
  • 类比：LangChain = "照着菜谱一步步做菜"；LangGraph = "边做边尝，咸了加水、淡了加盐，直到满意"。
  • 怎么选：简单一步到位的任务用 LangChain；"边做边想、错了重来"的复杂 Agent（如 ReAct 循环）用 LangGraph。

四、提示词 / 上下文 / Harness 工程

提示词工程的关键技巧有哪些？
  • 角色设定：明确身份、能力边界、语气（"你是资深后端工程师…"）。
  • 结构化与少样本（Few-shot）：给出输入→输出示例，固定输出格式（JSON/Markdown），降低解析失败。
  • 分步引导（CoT）：复杂任务要求"先分析再回答"；思维链 + 约束（只基于给定材料、不得编造）。
  • 划清边界：明确"不知道就说不清楚，不要胡编"；设置兜底话术。
  • 变量化 + 迭代评测：把可变部分抽成模板变量，用固定测试集回归对比不同 prompt 效果。
上下文工程在对话系统中的作用？
  • 信息不丢：多轮历史、工具结果、检索片段按需注入，保证模型"记得住"。
  • 控制成本与延迟：token 越多越贵越慢，通过裁剪/摘要/压缩把预算用在刀刃上。
  • 提升质量：缓解 Lost in the Middle，把关键信息放显要位置，减少超窗截断导致的失败。
  • 稳定性：统一 token 预算 + 状态机恢复，支持断流续跑、异常兜底。
Harness 工程是什么？在 Agent 开发中如何应用？
  • Harness 是包裹在 LLM 之外的工程脚手架/控制外壳：负责任务编排、工具调用、状态管理、重试、评测与观测，让"薄模型"变成"可落地的系统"。
  • 核心组成：循环控制（ReAct 循环、最大步数、终止条件）、工具/协议接入（Function Calling、MCP）、状态与上下文管理（记忆、压缩）、可靠性（重试、降级、超时）、评测与可观测（trace、指标、护栏）。
  • 应用：模型只做推理，工程能力沉淀在 Harness里——同一套编排可替换不同模型/工具，也便于灰度、回滚、A/B 评测。

五、场景题

场景题：设计一个旅游推荐 Agent，需要考虑哪些模块？
  • 意图理解：解析目的地、时间、预算、人数、偏好（亲子/美食/户外）等约束，缺失则反问澄清。
  • 工具层：机票/酒店/景点/天气/地图 API，通过 Function Calling 或 MCP 接入；
  • 知识/检索层：攻略、评价、政策（签证/防疫）用 RAG 召回，保证信息新鲜可溯源。
  • 规划与编排：ReAct 循环，把需求拆成多步（查景点→排行程→订机酒），支持多路并行。
  • 记忆模块：三层记忆——工作记忆存当前行程草稿，情景记忆存用户历史偏好，语义记忆存稳定旅游知识。
  • 生成与约束：输出结构化行程（天/时间/地点/预算），做预算校验、时间可行性校验。
  • 工程保障：SSE 流式、上下文压缩控 token、失败降级（某工具挂了给兜底推荐）、评测与监控。
