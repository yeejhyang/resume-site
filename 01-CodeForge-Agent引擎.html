项目介绍

项目介绍
💬 通俗版

我想让大模型代替程序员，你说一句「帮我做个待办清单 App」，它就能自己写代码、自己检查、把能用的成品交给你。但这个「自动写代码的机器人」一开始干得又慢又差——慢是因为它要来回传话、重复劳动；差是因为它写出的代码能编译，但打开页面却是空白的、按钮点了没反应。

我的工作就是帮这个机器人变快（少做无用功）和变好（真能跑起来再用）。

🎯 专业版

这是一个以代码生成 agent 为场景的课题，覆盖【澄清、规划、编码、构建、部署】全流程，核心围绕两件事：如何提效和提质。

  1. 与业务共同设计 20+ 端到端场景用例，通过全链路调用与耗时分析，定位问题；
  2. 在效率层面：针对原架构存在跨 Agent 上下文丢失、子 Agent 重复探索问题出发；提出【单主 Agent + 按需子代理】的优化方案，并结合三级上下文压缩提效；
  3. 在质量层面：针对部分用例出现的编译通过，但运行时异常问题；提出【构建校验 → 渲染断言 → 交互回归 → 修复验证】质检闭环方案。
① 如何发现问题？你做了哪些尝试？
💬 通俗版

就像给一辆新车做「测速 + 装行车记录仪」：先定好标准（能不能按时到、会不会出事故），再记录它一路干了什么。我让 Agent 做一批任务（比如生成待办清单 App），给它打分，再回放它每一步，问题就自己暴露了：

  • 慢的原因：负责"规划"的 Agent 想好了方案，负责"写代码"的 Agent 却看不到这个方案，只能自己从头把项目目录摸一遍（重复劳动）；几个 Agent 之间传话还容易传丢信息。
  • 差的原因：很多代码能"编译通过"，但打开页面是空白、按钮点了没反应——说明光检查"能不能编译"根本不够。
  • 还有一个坑：Agent 有时会嘴上说"修好了"，但回放记录里它根本没动手。
🎯 专业版

发现问题靠的是「可量化评估 + 可观测日志」双管齐下，让数据替我暴露瓶颈：

  • ① 量化评测：与业务共同设计 20+ 端到端场景用例，分 L1~L4 四档难度（L1 单页工具 → L4 迭代修改），记录 生成时长、一次构建通过率、需求达成率、缺陷率、修复成功率 4 个指标，让「好坏」变成可对比的数字。
  • ② 可观测日志：每轮工具调用打一行 [AGENT_SUMMARY]（exit 原因 / turns / 耗时 / token 进出），记录 18 种事件（tool_call / compact / subagent_spawn / recovery_attempt 等），可回放整条调用链。
  • ③ 用数据定位瓶颈：
    • 效率侧——通过全链路调用链与耗时剖析定位到多级委托的三大瓶颈：跨 Agent 上下文丢失（方案序列化传递被截断）、子 Agent 重复探索（各自从零 ListDir/Glob）、token 预算撞墙（上下文叠加触发输出截断）。
    • 质量侧——统计发现大量用例「编译通过但运行时异常」，证明只校验编译存在检测盲区。
    • 失真交付——审计 transcript 时发现「回复宣称已修复但无对应 tool_use」的假交付。

关键点：靠「量化指标 + 调用链日志」暴露，而非凭感觉——这是简历「数据驱动的架构决策」的依据。

② 针对问题你如何具体优化？为什么这么做？最终效果如何？
💬 通俗版

为什么这么改

  • 让它别传话：原来好几个 Agent 互相传话，容易传丢。改成一个人从头干到尾，最多偶尔找个帮手，就不丢信息了。
  • 让它别记太多：任务越长记录越多，塞给机器又慢又贵。改成只留关键信息，旧的无用记录先收起来。
  • 真刀真枪验收：原来只检查"能不能编译"，等于只看"语法对不对"。改成真的把页面打开、点一点按钮，看它能不能用。
  • 不许靠嘴过关：原来它会说"修好了"但没动手。改成用验证结果当证据，没证据就得真去修。

具体怎么做 + 效果

  • 提效：让主 Agent 自己拿着全部信息干活；对无用旧记录做三层"收纳"，先扔旧的、再压缩成一句话、最后才让机器做摘要。→ 做个 App 从 8 分钟降到 5 分钟（快 38%）。
  • 提质：构建通过后，用自动浏览器打开页面，检查是否空白、布局是否塌、按钮点了有没有反应；发现毛病就带着截图和定位告诉它哪错了，修完再复检；若它又想"光说不做"，就强制它真动手。→ 出错的比率从 29.5% 降到 17.1%（少 42%）。
🎯 专业版

一、为什么这样做（动机 / 设计取舍）

  • 提效 · 架构：多级委托痛点是上下文在传递环节丢失、子 Agent 重复探索、上下文叠加撞预算。原则——上下文由单点自持，委派层级越深损耗越大，故收敛为主 Agent 自干大部分活。
  • 提效 · 上下文管理：原则——能规则解决的不调 LLM，压缩按成本递增，仅在必要时升级到 LLM 摘要，短对话零额外开销。
  • 提质 · 质量闭环：只校验编译有检测盲区。原则——用真实渲染环境做运行时断言，暴露 DOM 挂载 / 布局塌缩 / 事件绑定类问题。
  • 提质 · 诊断与恢复：盲目重试既烧 token 又可能改坏别处，且模型易「嘴上说修好」。原则——给精确到根因的指引，并用客观验证器作最终判定。

二、具体如何优化（手段）

  • 提效 · 架构重构：多级委托 → 单主 Agent + 按需子代理，主 Agent 自持完整上下文完成规划+写码+验证；子代理降级为工具，仅保留隔离/并行子任务（task/explore），禁止递归派生、写任务强制串行。
  • 提效 · 三级上下文压缩：Snip 历史裁剪（对齐 tool_use/tool_result 配对，避免 API 400）→ Microcompact 零成本摘要（纯规则压一句话）→ AutoCompact LLM 摘要（长会话超阈值才触发，带熔断），并统一 token 预算。
  • 提质 · 质量反思闭环：「构建校验 → 渲染断言 → 交互回归 → 修复验证」四步，用 Playwright 真实浏览器做运行时断言，修复后重跑套件确认缺陷真消除。
  • 提质 · 结构化诊断 + 硬性恢复：缺陷输出 { severity, code, message, fixHint }（如 BLANK_BOARD_GRID + 根因提示 + 截图）驱动定向修复；对「无 tool_use 却宣称修复」的假交付用硬性恢复判定强制真调工具，最多 3 轮。

三、最终效果

  • 效率：生成时长 8 → 5 分钟（-38%）。
  • 质量：一次构建通过率 84.4% → 88.6%（L1-L3），缺陷率 29.5% → 17.1%（-42%），需求达成率 96.4%；L4 迭代修改均一次构建通过、1 轮对话完成。
  • 串讲：提效靠「架构重构 + 成本递增压缩」，提质靠「真实浏览器验证 + 结构化诊断 + 硬性恢复」，落到「生成快、缺陷少」。

一、技术架构详解

查询循环（Query Loop）的完整流程是什么？
💬 通俗版

可以把它想成「机器人边思考边动手的工作循环」：

  • 拿到你的需求后，它会想想、然后动手干活（比如打开文件、运行命令），拿到结果后再想想、再动手，如此循环，直到它觉得干完了。
  • 它每次动手前，会先把「太旧的记录」整理一下（清理历史），免得自己记太多变笨。
  • 如果它干着干着突然说「我干完了」，但没有实际动手证据，系统会把它拦回来继续干，防止它偷懒。
  • 为了防止死循环，它最多会循环一定次数（默认 60 轮），超了就停下来。
🎯 专业版

这是引擎心脏（queryLoop.ts），一个 while 循环 + 显式状态机的异步生成器：

用户消息 → ① 上下文预处理：snip(裁剪) → microcompact(微压缩) → sanitizeToolPairing(配对修复) → autocompact(自动摘要) → ② 构建 system prompt + 消息 + 工具定义，流式调用 LLM → ③ 解析响应：text / reasoning / tool_use → ④ 有 tool_use？→ 并行执行工具(StreamingToolExecutor) → 结果进历史 → 回到 ① └ 无 tool_use → 判断是否要"恢复"(防假交付) → 终止
  • 终止条件：LLM 返回 end_turn、达到最大轮次（默认 60）、用户中止、错误。
  • 状态机：用 TransitionReason 枚举追踪状态转换（next_turn/max_output_tokens_escalate/no_tool_call_recovery/compact_retry 等），每种转换独立重试上限，避免死循环。
  • checkpoint：每轮工具后把完整 messages 序列化到 agent_working_set，崩溃/断流可恢复完整轨迹。

二、上下文管理（提效主线）

三级上下文压缩具体是哪三级？每级的触发条件与实现？
💬 通俗版

像「整理一个越写越长的笔记本」，分三级由浅入深：

  • 第一级：扔旧页——最前面的旧记录没用了，直接扔掉，只留最近一截。
  • 第二级：写摘要——有些记录太长，用一句话概括它干了什么（比如"读了个 200 行的文件"），不花钱、不影响理解。
  • 第三级：请助手重写——笔记本实在太厚，就让机器（LLM）把整本内容浓缩成一份要点总结，再继续干活。

从"扔"到"请助手"，越来越费力气，所以只在必要时才用更高级的那级，大多数时候靠前两级就够了，省钱又省时间。

🎯 专业版
  • 第一级 · Snip 历史裁剪（snip.ts）：token 超过 autocompact 阈值 × 70% 时裁掉最旧段、保留最近 25% 窗口 tail。难点是 tool_use/tool_result 配对完整性——API 要求每个 tool_use 必有对应 tool_result，否则 400。用 sanitizeToolPairing：收集 tool_use id → 剔除孤儿 tool_result → 未应答 tool_use 追加占位；并对齐到安全边界（普通 user 轮次）避免后缀以孤儿 tool_result 开头。
  • 第二级 · Microcompact 微压缩（compact.ts）：零 LLM 成本的工具结果摘要，把超过 6 轮、超 200 字符的旧工具结果替换成一句话（如 [FileRead: src/App.tsx (200 lines) — content compacted]），不丢语义、不调 API。
  • 第三级 · AutoCompact 自动摘要（compact.ts）：长会话阈值降维，token 超 窗口 - 13k buffer 时调 LLM 压成结构化摘要（Task/Actions/Files/Decisions/Errors/Current State），再重注入工作目录、最近编辑文件、最新用户请求（withPostCompactReinjection）；带熔断——连续 3 次失败不再重试。
除了压缩，还有哪些 token 控制手段？
💬 通俗版
  • 给"读数"设上限：工具读出来的大段内容，先记个上限，太长的就截掉头尾、放个链接指向完整文件，避免撑爆记忆。
  • 给"写答案"兜底：如果机器写太长写到一半被掐断，系统会自动让它从断的地方继续，而不是从头再写一遍（防止它傻傻地重写一样的大段文字又卡住）。
  • 紧急抢救：万一系统报"记忆装不下了"，立即触发一次整理（压缩），成功后再接着干。
🎯 专业版
  • 工具结果预算（applyToolResultBudget）：工具结果进历史前按类别设上限（Grep/FileRead ≤20k、Bash ≤30k、Agent ≤50k），超限「留头留尾」截断，大结果溢写到磁盘 .spark/tool-results/ 并附路径。
  • 统一 token 预算：主 Agent 与 task 子代理共用同一预算（早期 8192 上限曾致子代理写大文件中途撞墙、烧 180s 返回 0 块，已修正）。
  • max_output_tokens 截断恢复：输出截断时——Stage1 静默升级 max_tokens 并注入「从断点继续，不要重复」；Stage2 注入恢复消息强制续写、建议拆小文件。避免「重复生成大输出又被截断」死循环。
  • 上下文溢出紧急恢复：API 报 prompt is too long 时立即紧急 compact，成功后用压缩消息重试。
为什么上下文管理对 LLM 应用这么重要？
💬 通俗版
  • 更贵：记的东西越多，机器思考和出结果就越慢、越费钱。
  • 更笨：信息太多时，机器会"丢三落四"——尤其容易忽略中间那部分内容，关键信息被淹没。
  • 更易翻车：超过它"记性"的上限，任务会直接失败。

所以要在不丢关键信息的前提下少记——这正是三级压缩的意义，短对话几乎不花额外成本。

🎯 专业版
  • 成本：token 越多，推理成本越高、首包越慢（每轮 prefill 都要重算）。
  • 质量：上下文过长会「丢失在中间（Lost in the Middle）」——模型对长文本中段信息利用不充分，关键信息被淹没。
  • 稳定性：超过窗口被截断，任务中途失败。
  • 故须「在信息不丢失的前提下压缩上下文」——三级压缩（历史裁剪 → 工具结果零成本摘要 → 长会话阈值降维）成本递增、仅在必要时升级到 LLM 摘要（短对话零额外 LLM 调用），并统一 token 预算，对应简历「三级上下文压缩」。

三、质量反思闭环（提质主线）

「编译通过但运行时异常」是什么问题？你的闭环怎么治？
💬 通俗版

相当于「作文语法都对，但读起来根本不通」。原来只检查代码"能不能编译"，就像只检查"句子语法没错"，但页面打开却是空的、按钮没反应——这些只有真正打开页面用一下才能发现。

我的办法是加一道「模拟真人验收」流水线：

  • 先编译：确认代码能跑起来、依赖能装上。
  • 再打开页面看：用自动浏览器把页面打开，看有没有报错、首屏是不是空的。
  • 再点一点：检查布局有没有塌、按钮点了有没有反应。
  • 修完再验：发现毛病让它改，改完重跑一遍，确认真修好了，而不是越修越坏。
🎯 专业版
  • 问题本质：传统只校验「能不能编译」，是检测盲区——编译通过 ≠ 功能正确。LLM 按概率生成 token，能写出「语法正确」代码，却不一定理解「运行时状态、DOM 挂载、事件绑定」等仅在真实环境暴露的问题，故出现首屏空白、布局塌缩、按钮没反应。
  • 反思闭环（RunVerificationSuite）：构建校验 → 渲染断言 → 交互回归 → 修复验证，每步补前一步盲区。
构建校验(bun install, 失败 fallback npm → bun run build) → 渲染断言(Playwright 监听 console/pageerror/请求失败/4xx，验证首屏与布局) → 交互回归(首屏完整性/布局塌缩/空按钮/点击反应 + 截图) → 修复验证(重跑验证套件确认缺陷消除)
  • ① 构建校验：基础门槛，保证能编译、依赖能装，是入口不是终点。
  • ② 渲染断言：把「能编译」推进到「能跑起来」，用真实浏览器监听 console/pageerror/请求失败/4xx。
  • ③ 交互回归：验证「能用」，渲染后 page.evaluate 做四项断言。
  • ④ 修复验证：修复后重跑套件确认缺陷真消除，而非修一个坏一个。
  • 输出结构化缺陷诊断（缺陷码 + 修复提示 + 截图）回传 Agent 驱动定向重生成，并以硬性恢复判定（verdict:FAIL 强制重试）拦截失真交付。
交互回归（interactionChecks）具体检查什么？
💬 通俗版

页面打开后，用自动浏览器替真人"看一眼 + 点一下"，主要查四个毛病：

  • 有没有内容：整个页面空空如也、一个字都没有 → 说明组件没挂载上。
  • 布局有没有塌：像扫雷这种九宫格界面，格子全挤成一团 → 布局样式写坏了。
  • 按钮是不是空的：一屏按钮全是空白、点也白点 → 数据算了但没显示出来。
  • 点了有没有反应：点最显眼的按钮，页面一点变化都没有 → 点击逻辑没接上。
🎯 专业版
  • 用真实浏览器（Playwright headless）在渲染后执行 page.evaluate，做四项断言：
  • ① 首屏完整性：BLANK_FIRST_SCREEN——正文无可见文本 → 根节点没挂载/容器塌缩。
  • ② 布局塌缩：BLANK_BOARD_GRID——grid 有面积但子元素 <20% → grid-template 塌缩（九宫格/扫雷类典型 bug）。
  • ③ 空按钮：EMPTY_BUTTON_CONTENT——≥80% 按钮空文本且 ≥20 个 → 内容变量算了但没渲染进 JSX。
  • ④ 点击反应：CLICK_NO_REACTION——点最显眼按钮后页面文本长度无变化 → click handler 没接状态。空白屏/无交互元素是硬 FAIL，点击无反应是 warning（避免误伤静态页）。
什么是「失真交付」？为什么 LLM 会这样？你怎么防？
💬 通俗版

就是机器嘴上说"修好了"，其实根本没动手。它可能真以为自己做了，也可能是想讨好你随便应一句。

我用两道保险来防：

  • 看它有没有动手：如果它说"修好了"但记录里找不到它真的去改代码/运行的痕迹，就把它拦回来，强制它真干。
  • 看验证结果：如果不通过自动验收，就要求它必须真的去改、再重新验收，不许光用文字糊弄。

核心一句话：以客观验证结果为准，不轻信机器自己说的。

🎯 专业版
  • 失真交付：模型回复「已修复/已完成」但实际没调用工具，属幻觉或「讨好式」输出。
  • 原因：LLM 按概率生成文本，可能「以为」自己做了。
  • 双重防范（queryLoop.ts）：
  • ① 伪造执行检测（shouldRecoverFromMissingToolCalls）：本轮无 tool_use 但回复含「已构建/已修复/已安装」宣称或假工具标记（<function_calls>）→ 注入 SYSTEM NOTICE 强制真正调工具，最多重试 2 次。
  • ② 验证失败强制修复：RunVerificationSuite 返回 verdict:"FAIL" 时注入指令「必须调真实工具修复根因并重新验证，不许用文字宣称完成」，否则强制重试。这是「编译通过但运行时异常」下最主要失效模式。
  • 核心思想：用客观验证器（真实浏览器断言）作最终判定，不信模型宣称。
「结构化缺陷诊断」是怎么设计的？「硬性恢复判定」又是什么？
💬 通俗版

这就像医生开诊断单，而不是只说"你有病"：

  • 结构化诊断：出问题时，不只是说"错了"，而是说清是什么毛病、错在哪、怎么修（比如"布局塌了，去检查九宫格的排列参数"），还附上页面截图让它亲眼看。
  • 为什么：让机器知道错在哪、按提示定向修，而不是瞎猜重来——瞎重试既费钱又可能把好的地方改坏。
  • 硬性恢复：万一它又想"光说不做"，就强制它必须真的去改、再重新验收，最多给 3 次机会。
  • 关系：一个负责"告诉它哪错、怎么修"（软），一个负责"逼它真的去修"（硬），一软一硬把质量兜住。
🎯 专业版
  • 结构化缺陷诊断：发现问题后输出 { severity, code, message, fixHint }。例如 code:"BLANK_BOARD_GRID" + fixHint:"检查 grid-template-columns/grid-auto-rows，避免依赖未解析 CSS 变量"，附截图路径。
  • 为什么这样设计：缺陷码让 LLM 精确对号入座，fixHint 指向根因，截图让它「看到」渲染结果——目的是定向修复而非盲目重试（盲目重试烧 token 且可能改坏别处）。
  • 硬性恢复判定：RunVerificationSuite 返回 verdict:"FAIL" 时强制注入「必须调真实工具修复根因并重新验证，不许用文字宣称完成」，否则强制重试，最多 3 轮修复循环。
  • 两者关系：结构化诊断「告诉哪里错、怎么修」，硬性恢复「逼真的去修、不许嘴上糊弄」，一软一硬兜底质量。

四、项目问题（从简历出发，面试官会深挖的）

简历说「跨 Agent 上下文丢失」，具体丢在哪里？你当时怎么发现的？
💬 通俗版
  • 丢在哪：就像项目经理写好方案，交给别人去做，但交接时方案"被精简丢了"。负责规划的人想好了文件、接口，转交给写代码的人时，这些信息在传递中被截断，写代码的人拿不到完整方案，只能自己重新摸索项目。
  • 怎么发现：看运行记录，发现写代码的人反复去翻目录、查文件（这些本该是方案里已有的），明显是在重复劳动。
🎯 专业版
  • 丢在哪：主 Agent 的方案需序列化塞进子 Agent（planner/coder/verifier）prompt，方案里的文件路径、接口契约、技术决策在传递时被截断/摘要，子 Agent 拿不到完整上下文就重新探索脚手架、做出与规划不一致的实现。
  • 怎么发现：通过 [AGENT_SUMMARY] 日志 + transcript 审计，看到子 Agent 大量重复 ListDir/Glob，以及主 + 各子 Agent 输入 token 叠加撞预算。
  • 结论：委派层级越深，上下文传递损耗越大。单主 Agent 让上下文「单点持有」，消除传递环节。
改成单主 Agent 后，什么情况下还会用子代理？
💬 通俗版
  • 只在"分工互不干扰、能各自独立完成"时才用帮手：① 几个不相干的文件要同时写，可以分头并行写；② 需要单独只读地调查/审查代码时。
  • 原则是尽量少用——主 Agent 自己就是主力，帮手只是"临时工具"，而且帮手不能再去招帮手（禁止递归）。
🎯 专业版
  • 只在「真正隔离、可自包含」的子任务用：① 互不相干文件的并行编写；② 需要独立上下文的只读调查/代码审查（explore）。
  • 原则「rarely」——主 Agent 是主要实现者，自己规划+写码+验证；子代理只是「隔离/并行」工具，且禁止递归。
简历说「工具结果零成本摘要」，为什么强调「零成本」？
💬 通俗版
  • 因为让机器（LLM）做摘要，等于额外再花钱请一次"人工"，既费钱又变慢。而我的"零成本摘要"是用固定套路直接压缩（比如把"读了个 200 行的文件"浓缩成一句话），不请机器、不花钱、也不慢。
  • 这也体现一个原则：能简单解决的绝不动用大模型，只有内容实在太多时才让它出马。
🎯 专业版
  • 用 LLM 摘要需额外一次 API 调用，花 token 又加延迟。Microcompact 的「零成本摘要」是纯规则（按工具类型拼固定模板），不调 LLM、不丢语义、不增延迟。
  • 体现分层思想：能规则解决的绝不调 LLM，仅长会话才触发 AutoCompact（LLM 摘要），短对话全程零额外 LLM 开销。
为什么一次构建通过率只从 84.4% 提到 88.6%，而缺陷率降幅更大（-42%）？
💬 通俗版
  • 因为这两个数字量的是不同的事："一次构建通过率"只看代码能不能一次编译过（偏语法问题，本来就不容易错，提升空间小）；"缺陷率"看的是跑起来能不能用（渲染、交互这种难问题，原来毛病多，改进空间大）。
  • 我的重心放在"能跑能用"这种更难的问题上，所以缺陷率降得最明显。
🎯 专业版
  • 两者度量不同维度：一次构建通过率是「编译能否一次过」（偏语法/依赖，基线高、空间小）；缺陷率是「运行时功能缺陷」（组件渲染、交互更难，基线差、空间大）。
  • 质量闭环重点攻运行时缺陷（编译过但跑不起来），故缺陷率改善最明显——印证「编译通过」≠「功能正确」。
如果让你重新设计，有哪些可以改进的点？
💬 通俗版
  • 让帮手能并行干：现在多个帮手共用同一个工作区，怕互相覆盖所以只能排队。将来可以给每个帮手一个独立的工作副本，互不干扰就能同时干了。
  • 更强的安全隔离：现在靠"规则检查"防危险命令，对外部用户最好升级成沙箱隔离，把危险操作彻底关在笼子里。
  • 更聪明的验收：现在靠文字长度、面积这种"经验判断"，以后可以用 AI 看图，像真人一样看出界面好不好看、对不对。
🎯 专业版
  • 子代理文件隔离：当前共享同一 workspace，写任务被迫串行。可像 claude-code 给每个子代理独立 git worktree，写任务也能安全并行。
  • 容器级隔离：当前 Bash 安全是「白名单+黑名单」进程级检测，对外部用户场景应升级为容器/sandbox 隔离。
  • 缺陷诊断自动化：交互回归目前是启发式（文本长度/面积），可引入截图 + 视觉模型做更智能 UI 断言。

五、可量化评估体系

你怎么设计可量化测试体系的？
💬 通俗版
  • 准备一批考题：和业务一起设计了 20+ 道真实场景题，从简单到难分 4 档（L1 单个小工具 → L4 在已有应用上改需求）。
  • 定好评分标准：每道题都量几个数字——做得快不快、一次能不能编译过、能不能满足需求、出错的比率、错了能不能自己修好。
  • 用分数说话：所有优化前后都用同一套题打分，哪个指标差了就去修哪里，形成"评测 → 定位 → 修复"的循环。
🎯 专业版
  • 20+ 业务场景端到端用例（与业务共同设计），分四档难度：L1 单页工具（8）、L2 列表/CRUD（7）、L3 全栈系统（5）、L4 迭代修改（4），建立分层验收标准。
  • 核心度量指标：生成时长、一次构建通过率、需求达成率、缺陷率、修复成功率，贯穿优化前后量化追踪，为架构决策提供数据归因，支撑「评测 → 定位 → 修复」迭代。
  • 分层结果：L1-L3 一次构建通过率 88.6%、缺陷率 17.1%、需求达成率 96.4%；L4 迭代修改均一次构建通过、1 轮对话完成（验证二次修改与上下文复用）。

六、通用八股（通用原理，结合项目答）

什么是 Agent？它和普通 LLM 调用有什么区别？
💬 通俗版
  • 普通调用：你问一句，它答一句，回答完就完事，不能自己动手做事。
  • Agent：除了会说话，还给你装了"手"和"记忆"——它能自己查资料、改文件、跑命令，做完一步看结果，再决定下一步，直到把整件事干完。
  • 就像从"一个只会出主意的顾问"变成"一个能独立完成任务的员工"。
🎯 专业版
  • 普通 LLM 调用：一问一答，输入 prompt 输出文本，无外部交互。
  • Agent：让 LLM 具备「感知 → 规划 → 行动」能力，能调用工具、观察结果、再决策，形成自主循环完成复杂目标。
  • 核心三要素：模型（大脑）+ 工具（手）+ 记忆（上下文）。CodeForge 把「写一个 CRUD 应用」拆成多轮工具调用（写文件 → 构建 → 验证 → 修复）。
什么是 ReAct 范式？为什么适合做 Agent？
💬 通俗版
  • ReAct = 边想边做：先想一想（该干嘛），再动一下手（去执行），看结果再想、再做……直到做完。
  • 对比"光想不做"和"光做不想"，它边做边根据反馈修正，特别适合要查资料、跑代码这种需要动手的任务。
  • 我的引擎就是这样：机器说"我要调某工具" → 执行 → 把结果喂回去 → 它再思考下一步。
🎯 专业版
  • ReAct = Reasoning + Acting：推理与行动交替。模型先 Thought，再决定调哪个工具（Action），拿到 Observation，继续思考，直到得出结论。
  • 对比纯 CoT（只推理不行动）和纯 Act（只行动不推理），ReAct 让模型边想边做、根据环境反馈修正，适合查资料、执行代码、多步操作任务。
  • CodeForge 查询循环就是 ReAct 工程实现：LLM 输出 tool_use（Action）→ 执行（Observation）→ 注入结果（下一轮 Reasoning）。
短期记忆和长期记忆有什么区别？怎么实现？
💬 通俗版
  • 短期记忆：就像这次对话里的"当下记忆"，内容都在手里，但容量有限、关掉就没了。
  • 长期记忆：像记到小本本里，下次还能翻出来用（比如存到数据库，需要时再调出来）。
  • 我的项目主要管的是短期记忆——怎么在有限容量里装下更多有用的（三级压缩），并能断线恢复。
🎯 专业版
  • 短期记忆：当前会话上下文窗口内历史，直接拼进 prompt，受窗口限制。
  • 长期记忆：跨会话持久化，通常用向量数据库存历史/知识，需要时检索注入。
  • 常见手段：摘要记忆（历史压摘要，对应 AutoCompact）、向量记忆（嵌入后检索）、知识库（结构化存储）。我的 Working Set 持久化 + 三级压缩属于短期记忆管理；「持久化摘要」跨会话复用接近长期记忆。
LangChain 和 LangGraph 是什么？StateGraph 是什么？
💬 通俗版
  • LangChain：一个"搭积木"框架，把模型、工具、记忆拼成一条顺序执行的链。
  • LangGraph：更灵活的"流程图"，用图来表达节点和跳转，支持循环、回退、条件分支，适合复杂任务。
  • StateGraph：LangGraph 的核心，用一份共享的"记录本"贯穿各个节点，大家都能读能写、按流程流转。
  • 我的引擎是自己写的状态机，但思想和它一致——用一个贯穿循环的"共享状态"。
🎯 专业版
  • LangChain：大模型应用开发框架，把 prompt、模型、工具、记忆封装成链（Chain）。
  • LangGraph：有状态、有循环的 Agent 编排库，用图描述节点和边，支持循环、条件分支、人工介入，比线性 Chain 更适合复杂 Agent。
  • StateGraph：LangGraph 核心抽象，用共享状态（State）贯穿节点，节点读/写状态、边定义流转，适合「多步、可回退、可循环」工作流。
  • 联系项目：CodeForge 是自研 queryLoop 状态机，但「共享状态 + 循环流转」思想与 StateGraph 一致——LoopState 就是贯穿循环的共享状态。
MCP 协议是什么？和 Function Calling 有什么区别？
💬 通俗版
  • MCP：一个"统一插座标准"（类似 USB-C），让不同模型应用都能用同一套方式接上各种工具和数据源，不用每家单独对接。
  • vs Function Calling：Function Calling 是某家模型内部让模型喊"我要调工具"的机制；MCP 是跨模型、跨工具的统一标准，同一个工具能被很多应用复用。
  • 三个角色：宿主应用（Host）、发起连接的（Client）、提供工具的（Server）。
  • 我的内置工具是"直连式"，而我的检索平台项目用 MCP 对接文献库，体现复用价值。
🎯 专业版
  • MCP（Model Context Protocol）：Anthropic 提出的标准化协议，让模型应用以统一方式连接外部工具/数据源，解决「每个工具单独对接」的碎片化问题，类比 USB-C。
  • vs Function Calling：Function Calling 是某模型厂商内部让模型输出工具调用的机制；MCP 是跨模型、跨工具的标准连接协议，一个 MCP Server 可被多个客户端复用。
  • MCP 三角色：Host（宿主应用）、Client（发起连接）、Server（提供工具/资源）。
  • 联系项目：CodeForge 内置工具是「直连式」Function Calling；另一检索平台项目用 MCP 对接 Semantic Scholar 做论文搜索与引用分析，精读全文时通过它的 externalIds 映射到 arXiv 拉全文，体现标准化复用价值。
